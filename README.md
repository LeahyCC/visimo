# visimo

A music visualizer package built on one persistent canvas. Give it an `<audio>` element; bands, onsets, key and song structure drive a handful of small pieces called studies, and a post stack, through JSON casts.

WebGPU is preferred. The fractal ink also runs through WebGL2 when no WebGPU device is available; the fluid needs compute and so needs WebGPU. A study with nothing to draw it on the available backend is skipped, and if nothing in the cast can be drawn the host receives `onUnsupported`.

It was built inside [Musimo](https://github.com/LeahyCC/musimo) and pulled out so scenes and presets could be worked on against a bench rather than a music library. Musimo consumes it as a git dependency and is still the main user.

## Install

```sh
npm install github:LeahyCC/visimo#v0.2.0
```

`react` is a peer dependency. Git is needed to install it, which matters in a container: `node:*-slim` images have no git.

### It ships TypeScript, not a build

There is no `dist`, no declaration emit and no build step. The four `exports` point straight at `.ts` and your bundler compiles them. That is not a shortcut, it is the only shape that works: the feature worker is constructed as

```ts
new Worker(new URL('./features.worker.ts', import.meta.url), { type: 'module' })
```

and a library build either swallows that pattern into its own assets, where the consumer never finds it, or leaves a URL nothing emits a worker for, which 404s at runtime. Shipping source hands the pattern to the consumer's bundler, which is the one that knows where the worker should land.

Two consequences for a host on Vite:

```ts
// vite.config.ts
export default defineConfig({
  optimizeDeps: { exclude: ['visimo'] },
})
```

Without it the dev server dies during dependency optimization: the pre-bundler cannot load a `?raw` import out of `node_modules`, and the shaders are all `?raw`. The same exclusion keeps the worker's asset URL intact in a build.

And the package is compiled by your toolchain, so it wants a TypeScript at least as new as the one it was written against (7.0), with `resolveJsonModule` on for the preset files.

## Use

Four entry points, deliberately. A single barrel would drag the whole WebGPU tree into your main bundle.

| Entry            | What is in it                                                                     | Where it lands                |
| ---------------- | --------------------------------------------------------------------------------- | ----------------------------- |
| `visimo`         | `VisualizerStage`, `renderer`, `hasWebGpu`, `FeatureClient`, `F`, `PACKET_LENGTH` | import it lazily, about 38 KB |
| `visimo/audio`   | `attachAudio`, `resumeAudio`, `audioGraph`, `FFT_SIZE`                            | lazily, about 550 B           |
| `visimo/presets` | `PRESETS`, `STUDIES`, `parseCast`, `presetOrDefault`, `stepPreset`, `POST_LANES`  | your main chunk               |
| `visimo/catalog` | `SCENE_IDS`, `SCENE_LABELS`, `FLUID_SIZES`, `isSceneId`                           | your main chunk               |

`presets` and `catalog` touch no GPU and no WGSL, so a picker can be drawn without loading the visualizer at all. That split is the whole reason there are four of them. The `presets` entry is still called that and still exports the five names 0.1 had, which now hold pinned casts; see [Upgrading from 0.1](#upgrading-from-01).

Audio first, from the element's `play` event:

```ts
element.addEventListener('play', async () => {
  const { attachAudio } = await import('visimo/audio')
  await attachAudio(element)
})
```

`attachAudio` takes one element and one only. A `MediaElementSource` can be built just once per element, and on media served without CORS headers the browser silences it permanently, so the host has to pick the element it knows is same-origin. A second element is refused rather than broken. Call `resumeAudio()` when the page becomes visible again; browsers suspend the context behind a hidden tab.

**The picture does not depend on the volume.** A media element's source comes out after the element's own volume, so the graph takes the volume back off before the analyser and puts it back on after it (`volumeGains`), following `volumechange`. Without that a listener who turned the player down got a different picture: on the same ten seconds of a drop the treble band read 13 hits and a level of 0.77 at full volume and no hits and 0.16 at a volume of 0.08, because the top bands are the quietest in any mix and fall under the detectors' floor first. It holds down to a volume of 0.01. A muted element, or one at a volume of nothing, is exact silence and nothing brings it back, so a host that wants the picture with the sound off should route its own mute after the graph.

Then the stage:

```tsx
const Stage = lazy(() => import('visimo').then((m) => ({ default: m.VisualizerStage })))

<div style={{ position: 'relative' }}>
  <Stage
    hud={hud}
    preset={presetOrDefault(chosen)}
    fluidSize={512}
    onUnsupported={() => setFallback(true)}
  />
</div>
```

Both canvases are `position: absolute; inset: 0`, so **give them a positioned parent**. They carry no stylesheet; `className` and `hudClassName` are there if you want to restyle them.

| Prop             | Required | What it does                                                                                  |
| ---------------- | -------- | --------------------------------------------------------------------------------------------- |
| `hud`            | yes      | draws the overlay; the host owns the key that toggles it                                      |
| `preset`         | yes      | a pinned cast to draw, or `"auto"` to let the song choose. See [The director](#the-director)  |
| `fluidSize`      | yes      | the fluid's grid, from `FLUID_SIZES`. One control, every fluid                                |
| `startCharacter` | no       | where the character reader opens, as a partial of the five axes                               |
| `track`          | no       | any value that changes with the track, an id or a url. The director starts again when it does |
| `playhead`       | no       | a ref to anything with `currentTime` and `duration`, such as your `<audio>`. See below        |
| `onCharacter`    | no       | the character once it settles and rarely after, to save for next time                         |
| `onUnsupported`  | yes      | nothing can start or recover on an available backend: show artwork                            |
| `onBackend`      | no       | `webgpu` or `webgl2`, after attachment                                                        |
| `className`      | no       | goes on the scene canvas                                                                      |
| `hudClassName`   | no       | goes on the HUD canvas                                                                        |

Everything optional is new in 0.2 and nothing about it changes what a host that leaves it out already gets.

**Telling it where the track is.** A host that plays a file knows the position and the length, and the director cannot: it hears the music a frame at a time. Hand the stage the same ref you put on your `<audio>` and it reads `currentTime` and `duration` itself on every frame it draws:

```tsx
const audio = useRef<HTMLAudioElement>(null)
<Stage playhead={audio} ... />
```

It is a ref and not a number for one reason: a position changes several times a second, and a prop that changed that often would re-render the host and the stage for a value only the renderer reads. The ref is handed over once, nothing is called per frame, and it follows a seek and a new track without anyone saying so. A host with no element passes a ref to any object that has the two fields, in seconds. A `duration` that is not a length (`NaN` before the metadata loads, `Infinity` for a stream) is read as none given. With it the last stretch of a track reads as an outro whatever it is doing, and a short track has a short intro; see [The director](#the-director). Leave it out and both are read as they were.

`onUnsupported` fires when nothing in the chosen cast can start or recover on an available backend. `hasWebGpu()` only checks whether the WebGPU API exists; it neither guarantees an adapter nor detects the WebGL2 fallback. Do not use it to block loading Prism. The optional `onBackend` callback reports `webgpu` or `webgl2` after attachment.

### The `data-*` attributes are public API

The scene canvas carries, on attach and then throttled to 500 ms:

| Attribute       | What it says                                                                                  |
| --------------- | --------------------------------------------------------------------------------------------- |
| `data-adapter`  | the adapter, as its info describes it                                                         |
| `data-frame-ms` | the frame time                                                                                |
| `data-scene`    | the scene the cast draws as, derived from its inks; see Casts below                           |
| `data-detail`   | what is drawing, such as `512 fluid`, and the flow under it when nothing else names that grid |
| `data-post`     | the post stages running, or `off`                                                             |
| `data-preset`   | the pinned cast's id, or `auto` while the director is choosing                                |
| `data-cast`     | the live study ids, in cast order, space separated                                            |

They exist for tests and screenshots and Musimo's e2e suite asserts on the first six. Breaking one breaks a consumer silently, so treat them as the interface they are; the shipped casts print what their presets did, and `data-cast` is new in 0.2. One behaviour changed on 2026-09-20: a host that pins `wash` or `drift` is now given Plume, and `data-preset` prints `plume` for either, since the canvas reports the cast that is drawing and not the id it was asked for; see [Plume](#plume). All of them say what is really being drawn, so under the director they follow the cast it chose, and on the WebGL2 fallback they say what that path drew rather than what was chosen for it. The fractal's `data-detail` includes its internal render dimensions, allowing a canvas and draw size mismatch to be diagnosed.

## The demo

```sh
npm install
npm run dev
```

The demo opens Prism. Drop a track on the left and tune on the right. Files become object URLs on the same `<audio>` element and use `attachAudio`, as they do in a host app. Play/Pause buttons and labelled seek/volume controls replace the native media widget after repeated in-app browser crashes during testing. A cast with no fractal ink in it is disabled when WebGL2 is active, since nothing else in a cast draws there; Melt stays selectable and shows as Prism with a still trail.

**Auto** is the first entry in the picker and pins nothing: the song chooses the cast, as [The director](#the-director) describes. Under it the knobs give way, since there is no pinned cast to tune, and what is left is the panel that reads the director ten times a second: what is live and the fade each of them is at, the six moment weights, the five character axes and how settled they are. That panel is drawn under a pinned cast too, because the song is read either way, and the line under it says what `onCharacter` last handed the page, which is what a host would save against the track. Auto stays selectable on WebGL2: the fractal is all that path can draw, so it draws Prism's in place of whatever was chosen.

**Bench** is the other mode of the same panel: it solos a study, or a small cast, under sliders for character and moment and a synthetic packet, and keeps its setup in the URL hash. See [The study bench](#the-study-bench).

Vite is pinned to `http://127.0.0.1:5174/` with `strictPort: true`; it fails if that port is occupied instead of silently moving. Keep the server process running. A cached page can remain open after the server exits while its feature worker and hot-reload connection fail. During diagnosis, port 5174 had no listener and the stale page was trying a hot-reload connection on 5173. A persistent background Vite process restored the correct endpoint.

If graphics cannot start, **Retry graphics** mounts a fresh stage while retaining the audio element and its track. After failed WebGPU recovery, the stage replaces its scene canvas once so WebGL2 can acquire a fresh context. A canvas previously used for WebGPU cannot switch context type in place. The console logs unavailable APIs and initialization failures.

Every control is generated from the lists the package keeps: the cast's studies from the registry, each study's knobs from `IMPL_KNOBS`, the canvas's from `CANVAS_KNOBS`, the mapping vocabulary from `STUDY_FIELDS` and `CURVES`. Add a knob or a study to the package and it appears here with nothing to change, though a knob whose range is not obvious wants a row in `RANGES` in `demo/controls.tsx`. The panel is one block per study the cast holds, flow first and look last, and what a slider writes is an override on that study rather than the study itself, which is what a cast is allowed to change. The preset picker is grouped: Auto, then Presets (the shipped casts), then Flows, Inks and Looks, which list every study in the registry by name. Choosing a study pins a one-off cast built for it, id `solo:<study id>`, with the partners it needs to be seen (a flow gets the dye or the ribbon, an ink gets a flow, a look gets the lazy fluid and the dye) and never two studies that exclude each other; `demo/soloCast.ts` builds it, so a study added to the registry appears with no change to the demo. **copy cast** puts the whole thing on the clipboard as JSON that `parseCast` accepts; drop it into `src/studies/casts/` and add it to the list in `src/studies/casts/index.ts`. **reset** puts every number back to what the cast file holds, and is greyed out until something is touched, so it also answers whether the panel has drifted from the file. H toggles the HUD. F opens full view and Esc returns. The grid control appears whenever a cast holds the fluid, whether as the thing being drawn or as the flow under something else. The study bench the handoff asks for, where one study is soloed against sliders for character, moment and tension, is a later card.

What updates without a reload, measured by editing each file while the demo ran:

| Edit                         | Live                                      |
| ---------------------------- | ----------------------------------------- |
| `demo/*.tsx`                 | yes, React Fast Refresh                   |
| `src/shaders/*.wgsl`         | yes, the pipelines recompile              |
| `src/scenes/fluid.params.ts` | yes, the next frame reads the new numbers |
| `src/studies/casts/*.json`   | only through a full page reload           |

The shader row was checked rather than assumed: a hot update that recompiled nothing would look the same as one that did, so the sim shader was fed WGSL that cannot parse and the GPU raised the error straight away. The demo now keeps its component in `demo/App.tsx` and creates the React root only in `demo/main.tsx`. This avoids duplicate roots when a dependency changes. Hot replacement disposes the old renderer, releases its implementations, post stack and audio worker, removes its GPU-loss listener and cancels pending attachment. Ordinary stage unmounts still retain what the implementations hold. GPU module changes can restart those resources, so use the sliders for uninterrupted tuning and reload when changing cast files.

## How it works

### Audio graph

One `AudioContext` and one `AnalyserNode` (`fftSize` 4096, no smoothing; the extractor smooths per band), in `src/audio/AudioGraph.ts`. 4096 rather than 2048 because the low bands need it: at 2048 a bin is 23.4 Hz and the whole 20 to 60 Hz sub band was two bins wide. The cost is an 85 ms window instead of 43, so transients smear a little and the per-band onsets fire slightly softer; that is the trade, and it is one constant to put back. It is a module singleton, so it survives any remount.

The source is attached only once the context is running. A context built outside a user gesture starts suspended and a source on a suspended context is silent, so `attachAudio` resumes first and checks `state === 'running'` before creating the source. If the browser refuses, the track still plays on its own and the next `play` tries again.

The analyser is read for its waveform as well as its spectrum, for the ribbon in the post stack. `FeatureClient` calls `getFloatTimeDomainData` on the main thread on every `pump`, into one `Float32Array` of `fftSize` samples (4096, about 85 ms of sound, oldest first) that it allocates once and exposes as `waveform`, so a frame costs no allocation. It never goes to the worker and `features.protocol.ts` is unchanged: the extractor has no use for it, and a second buffer to transfer each frame would buy nothing. It is read before the client checks whether the worker still holds the spectrum, so it is fresh on every tick the renderer draws even when a reply is late, and it is read on the main thread's fallback extractor as well.

`src/audio/waveform.ts` turns it into the few hundred points a line is drawn from, in two pure functions that know nothing of what the points are for. `windowStart` gives up some of the newest samples to find a rising zero crossing, the first sample not below zero after one that is, and starts the window there, so a steady tone begins its line going up through the middle every frame instead of sliding sideways; with nothing to cross, which is silence or a level held on one side of zero, it takes the newest window. `resampleWaveform` averages that window down into the buffer it is given. Each output is the mean of a few evenly spaced linear reads across the samples it stands for rather than every Nth sample, so a hat far above what 256 points can show comes out as a faint wobble and not a false slow wave, and a span shorter than the buffer still comes out smooth. Anything that is not a finite number counts as silence, so no NaN can reach the GPU, and the amplitude is left alone: a sine in is the same sine out. How much sound the ribbon shows is the params layer's choice (`RIBBON_SPAN` and `RIBBON_SEARCH` in `post/params.ts`). The points are then levelled against their own loudest recent sample (`levelWaveform`, up at once and down over three seconds), because the analyser hears the element after its volume control and a listener at a tenth of full volume would otherwise get a tenth of a line. Under a peak of 0.02 the line is left to shrink, so the hiss of a paused track is not blown up to full height.

### Feature extraction

`src/audio/FeatureExtractor.ts` turns each analyser frame (dB per bin, plus the seconds since the last one) into a 52-float packet. It is pure TypeScript and normally runs in a worker (`features.worker.ts`, protocol in `features.protocol.ts`). If worker creation, loading, message decoding or sending fails, `FeatureClient` switches to the same extractor on the main thread, rebuilding the transferred spectrum buffer and ignoring stale replies. Analysis continues, with its CPU cost now on the rendering thread. The spectrum buffer is transferred to the worker and handed back with each packet. The client accumulates the time of render ticks skipped while the worker is busy. The renderer retains continuous levels between replies but consumes each packet's hit events only once, so slower replies cannot duplicate splats.

In order:

- dB to linear magnitude, then five log-spaced bands: sub 20 to 60 Hz, bass 60 to 250, lowMid 250 to 1k, highMid 1k to 4k, treble 4k to 16k. Each band is the root mean square of its bins, then an envelope with its own attack and release (sub 20 and 250 ms, treble 5 and 90 ms), then scaled by the loudest that band has been in the last few seconds, so a quiet track fills the same 0 to 1 as a loud one.
- A bin is centred on its own frequency and covers half a bin either side, and `bandFilter` weights it by how much of that span falls inside the band. Rounding each edge to the nearest whole bin instead put the 20 to 60 Hz sub band at 23 to 70 Hz, which is a tenth of the bass band sitting inside the sub one, so a bass note read as a kick. Weighted edges make a band cover the Hz it asks for at any FFT size, and the one bin two neighbours straddle is split between them rather than claimed by both or rounded away. What it cannot fix is the analyser's own window, whose main lobe is about three bins wide, so a pure tone always spreads into its neighbours; that is why a band can still hear a fraction of a hit just over its edge.
- The level is the root mean square rather than the mean of the magnitudes, which is what the energy in a band is and what `energy` already used over the whole spectrum. A mean divides one bright partial by the whole band: the same power gathered into a single bin read about the square root of the bin count lower, a factor of over twenty in a 512-bin treble band.
- Each band also detects its own onsets, in the same pass. The rise of each bin over the last 30 ms is already being read there, so a band's own half-wave rectified flux costs a subtract per bin and no second sweep; it is divided by the band's width like the level is, so a wide band and a narrow one reach their detectors on the same scale. Every band then gets its own copy of the detector below, with its own rolling window. That is the whole point: a band that is always busy settles on a high threshold and a quiet one on a low threshold, so the hats keep firing through a passage the kick is sitting out, and one emitter can answer the kick while another answers the hats. Each band publishes the frame it fired on, carrying that hit's strength, and a pulse that decays from it. In the same pass each band also measures where its rise sat across the spectrum and how wide it was: the rise-weighted mean and spread of the bins' places in octaves from 20 Hz to 16 kHz, as fractions of that span. They are written every frame and mean something on the frame the band's hit fires, which is what lets an ink give a sound a place of its own.
- `energy`: RMS from 20 Hz to 16 kHz, smoothed and scaled the same way.
- `flux`: half-wave rectified spectral flux, measured on log magnitude rather than raw. `log1p(1000 x magnitude)` per bin, the gain being that large because the magnitudes are small and `log1p` of 0.01 is 0.00995, which compresses nothing. On raw magnitude the same musical hit produced about ten times the rise in a loud passage as in a quiet one, so each detector's sensitivity drifted with the mix instead of staying fixed on the music. The rise is measured against the frame from 30 ms ago rather than the last one, whatever the frame rate: two analyser reads a frame apart overlap by 45% at 60 frames a second and by 92% at 144, so a per-frame rise shrank as the display got faster, and on a 144 Hz display the detectors were firing two or three times a second on the jitter between reads, through a sustained pad, at a rate that halved when the frame rate did. The onset threshold is the mean plus 2.5 standard deviations over a 1.5 second window, a span of time and not a count of frames, measured before the current frame joins it. An onset is flux rising through that threshold and at least 0.2 above the window's mean, at most one per 80 ms. The floor is the part that keeps a quiet passage quiet: the threshold is relative, and mean plus a few deviations of nearly nothing is a bar anything clears. On a real track the jitter of a pad reached 0.19 in every band, a hat spread across the treble band 0.3 to 0.6 and a kick in the sub band 1 to 3, so 0.2 sits in the gap; a band under four bins wide gets it raised by `sqrt(4 / bins)`, since it averages nothing out. `onsetStrength` grades the hit against the loudest recent one, since flux over its own mean is 1 on average and would hide hits in sustained music. `beatPulse` jumps to 1 on an onset and falls to 1/e in 180 ms.
- `tempo`: in `src/audio/TempoTracker.ts`, twice a second, the autocorrelation of the last 8 seconds of the bands' own flux, over the lags that mean 60 to 200 BPM. Each band's rise is resampled to 100 Hz (each 10 ms sample the average of the frames that overlap it, since the rise is a level that holds for the 30 ms it is measured over), put over its own mean and compressed with `log1p(3 × flux / mean)`, because a few big hits otherwise own the correlation and the beats between them do not register. The five are then summed, each weighted by how periodic it is on its own, and the sum is what is correlated. That is the part that matters: the whole spectrum's flux was really the treble's, since a thousand of its bins are treble and four are sub, so a kick barely registered and what it measured was the snare and the hats; and the beat in most music is not in any one band but is the kick and the snare taking turns, which only the sum sees as one pulse. Correlations are normalised by overlap and measured out to four times the slowest lag, so each lag can be scored with half its double and a quarter of its quadruple added in; before, the correlations stopped at the 60 BPM lag, so nothing under 120 BPM had a harmonic to its name and a dotted figure could outscore the beat with nothing to say it was no level of the metre. The score is weighted toward 120 BPM by a log-Gaussian 0.9 octaves wide, when the half lag correlates at least 0.6 as well it wins, and a period an octave from the one already reported has to outscore it by 15% to take over, so the beat and its half-bar, which often score within a few percent of each other, cannot flip every few seconds. The winning lag is refined between samples with a parabola through its neighbours, since one sample is 2% of a tempo. The first reading comes at four seconds from the part of the window that has filled; the reported value is the median of the last five, and it stays 0 until one lag clearly wins. Alongside it come a confidence, the correlation at the chosen lag averaged over those readings, and the beat phase: a pulse train at the period is laid over the last four seconds of the summed envelope and slid to where the onsets are, and the phase then runs forward on its own between estimates, nudged a third of the way toward each new measurement, so a study can anticipate the next beat rather than react to the last one.

The layout is at the top of the file, 52 floats read by name through `F` and never by a literal index: 0 to 4 the five band levels, 5 to 9 each band's own hit, 10 to 14 each band's pulse, then 15 energy, 16 and 17 flux and its threshold, 18 to 20 the global onset, its strength and the beat pulse, 21 the tempo guess in BPM, 22 and 23 time and the frame step, 24 to 27 four of the five that describe the song rather than the frame, 28 to 30 the harmony, 31 to 33 the structure, 34 to 43 where each band's hit landed and how wide it was, 44 and 45 the tempo's confidence and the beat phase, 46 `hardness`, which belongs with 24 to 27 and sits at the end because that is the only place a row may go, 47 to 50 the moment: `tension`, `release`, `rest` and `impact`, and 51 `grit`, which belongs with 46 and is at the end for the same reason. Rows are only ever added at the end, because the indices are public.

The global rows are the same detector run over the whole spectrum. They stay because the post stack reads `beatPulse`, presets map `flux` and `onsetStrength`, and the overlay draws the flux trace.

Nothing on the GPU reads any of this. Every consumer takes the `Float32Array` on the CPU, so there is no vec4 alignment to keep and the packet grows freely. The renderer used to upload it as a uniform buffer no shader bound; that buffer is gone.

`F` and `PACKET_LENGTH` are exported from the package, so this layout is public API. Musimo pins visimo at a tag and nothing here reaches it until a new one is cut.

### The song rather than the frame

Everything above answers what the music is doing in the last few milliseconds. Six more answer what kind of track it is and where in it we are, so a ballad and a drum and bass track can look different without a preset being swapped. They are levels in 0 to 1 like any other and a preset reads them through the same mapping table, which is why this needed no new machinery: `value = resting + Σ gain x curve(feature)` was already the right arithmetic and had only ever been given fast features.

All six are slow on purpose. The point is a number that has made up its mind, not another thing that flickers.

- `pace`: audible hits a second, each hit decaying away over half a minute, scaled so 4 a second is full. It counts a hit in any band rather than the global detector's, because a kick that lives in three sub bins barely moves the flux of the whole spectrum. It is a decayed count rather than a rate measured between hits, so it needs no memory of when the last one was and cannot spike on one close pair. A struck sound is one hit however many bands it trips: `pace` counts the hits the windows of `hardness` close (an onset in any band that lands inside an open tenth of a second window joins it), and each is worth its lift over the bed, 0 for a hit that barely moves the mix and 1 for one that is most of what is sounding. Settled on synthetic patterns it reads the rate of audible hits exactly, 2.13 a second for four to the floor at 128 and 2.90 for a two-step at 174, which is the kicks and snares and not the hats under them, and the same at 60 and at 144 frames a second. On the three tracks below it reads 0.35 for hardstyle, 0.30 for house and 0.27 to 0.30 for lo-fi after 25 seconds (a half-minute decay is a little over half way to settled by then), and each agrees with itself to within 0.01 across 60, 120 and 144 frames a second. **This is the one to reach for when what you mean is "fast".**
- `swell`: loudness now against loudness over the last half minute, in dB, centred so a steady passage sits at 0.5, six dB up is 1 and six dB down is 0. In dB rather than as a ratio so the two directions are the same distance from steady: as a ratio, half the loudness was already the floor and one and a half times the ceiling, so a preset could thin a knob in a breakdown far more easily than lift it in a drop. Centred rather than starting at zero so one row can lift a knob in a drop and another thin it in a breakdown, from the same feature with opposite gains. It reads the raw RMS and deliberately not `energy`, which is divided by its own recent peak and therefore sits near 1 through any steady passage however loud; a feature built on that one could never see a chorus coming. The long arm is held to the short one until it has seen a full window, because a cold envelope climbs from zero while the short one is already there, and without that every track's first half minute reads as a permanent drop.
- `weight`: where the spectral centroid sits, over about ten seconds, 1 for a track that is all sub and bass and 0 for one that is all highMid and treble. The centroid is the power-weighted mean of log frequency across the span, mapped between where it would sit for a flat spectrum filling the low group and one filling the high group, so it measures the balance of the spectrum and not which bands are occupied; the measure it replaces read the normalised band levels, and two bands that both had content both normalised towards 1, so anything with a kick and a hat in it sat at 0.5. Equal power per octave reads about 0.6, since the low group is fewer octaves wide than the high one, and white noise, most of whose power is above 4 kHz, reads bright. Silence holds the last reading rather than reading noise. Meant for colour and plume size rather than for activity.
- `hardness`: how abrupt and how saturated this track's hits are, as a running mean over the hits of roughly the last twenty seconds. `onsetStrength` cannot stand in for it: that grades a hit against the loudest recent hit, so it says how big this one was for this track and nothing about whether its hits are sharp or soft in general. Everything is measured against the bed the hit arrives over rather than against the mix: a level that falls to the RMS at once and creeps back over 300 ms settles between hits on whatever sustains under them, and the hit's window is the rise above that. Two numbers per hit. How much of the hundred milliseconds after it that rise holds near its own peak, as the mean of the rise over its peak, which is what a clipper and a limiter between them do to a sound; and how much of the spectrum the hit's power is spread across, the mean magnitude squared over the mean square, 1 for a flat spectrum and one over the bin count for a single partial, which is what distortion does to a sine. They are combined as a geometric mean, so a hit has to do both, and a hit that barely lifts the mix over its bed is scored as soft rather than on the shape of a rise that is mostly noise. Each hit's score goes into a decayed sum over a decayed count. On three synthetic tracks in `synthetic.ts` that differ only in the voice on the beat, the hats and the pad, all held to the same RMS: hardstyle (a clipped kick at 150, loud hats, no pad) reads 0.93, house (a plain kick at 124, loud hats, a light pad) 0.62 to 0.65, and lo-fi (a soft pulse at 80, quiet hats, a heavy pad) 0.05. Isolated clipped kicks read 0.87 to 0.89 and isolated soft pulses 0.06 to 0.09; a pad with nothing struck in it reads 0.11. It starts at a neutral 0.5, carried as a prior worth four hits rather than as a value held until a threshold, so it leaves the middle as fast as the evidence arrives and never steps; a track that has not been heard yet is not a soft track. Silence steps neither half of the ratio, so it holds where the last sound left it, the way `weight` holds its centroid. `character.ts` reads it, as a third of the hardness axis of the song's character; `grit` below is the other two thirds.
- `grit`: how dense and how unrelenting the sound between the hits is, over about ten seconds. It is the half of "is this a hard track" that no hit can answer, and the half that matters most on real music: a wall of distorted guitars has few sharp hits over its own sustained level, so three metal tracks read 0.11 to 0.12 on `hardness` against hip hop's 0.37. Three slow means, each a ratio of the sound to itself so a volume control cannot touch any of them. How much of the spectrum each frame's power covers, which is the same flatness a hit's hardness reads, taken every frame rather than per hit, and which is what distortion and noise do to a spectrum. What share of that power sits between 1 and 4 kHz, where a distorted guitar and a saw lead live and a pad and an upright bass do not. And how near its own recent peak the level sits, which is `energy`, and is how much room the master left itself. The first two multiply, the upper mids counting for twice the density, so a track has to do both: a cymbal wash is dense and lives above the mids, and a horn section fills the mids and is a handful of partials. The dynamic range then trims up to two fifths off what is left, so a hard track that breathes is still a hard track. Measured over 60 to 150 seconds of twenty tracks with `scripts/character-table.mjs`: August Burns Red 0.75, Subtronics 0.69, Pendulum 0.70, Bring Me The Horizon 0.70, the demo's dance track 0.82, house 0.45, hip hop 0.36, the Four Tet remix 0.20, Emancipator 0.06, Wilco and Christian Loffler 0.00. It reads the same at 60 and at 144 frames a second, and silence holds it where the last sound left it, the way `weight` holds its centroid.

- `tempo`: the BPM guess across 60 to 200, smoothed over five seconds. The raw guess steps when the tracker changes its mind, and the ramp is the only reason the normalised one is worth having: the picture drifts rather than lurching. A guess of 0, meaning nothing has settled, holds the ramp where it is rather than dragging it to nothing. **Gate anything built on it with `tempoConfidence`**, below.

What `hardness` cannot tell apart is anything faster than the analyser's window. At `fftSize` 4096 a frame is 85 ms of sound, so a hit that reaches full in 5 ms and one that takes 40 look the same going up: both fill the window inside one frame. What separates the synthetic pair is that the soft one takes 120 ms, which is longer than the window. Anything under about a tenth of a second of attack is one sound to this measure, and what still separates two such hits is the second half of it, the spread. Both halves need the hit to be audible over what is under it: a kick under a pad six times its own size lifts the mix by a hundredth, and such a hit is scored as soft because the shape of a rise that small is noise, not because it was heard to be soft. It is frame-rate independent to within 0.035 between 60 and 144 frames a second, measured across all three tracks above and the isolated pair. A 20 dB level change moves it by under 0.03 as long as the mix stays clear of the -60 dB floor the rest of the file uses, and the lo-fi track is the exception that shows where that floor is: it is mostly pad, so 20 dB down it straddles the floor and reads 0.35 rather than 0.05. Under the floor nothing is heard at all and the value holds rather than reading.

How `pace` got to counting hits, and what is left. It used to count the frames with an onset in them, and that made it read the display. One struck sound trips several bands and the sub band trails the rest by about 70 ms, so a kick was one count when those onsets shared a frame and two or three when they did not, and a faster display splits the same kick over more frames. The three tracks read 0.24, 0.17 and 0.25 at 60 frames a second and 0.38, 0.32 and 0.38 at 144, though hardstyle's four low bands fired on the same 62 kicks at both. The detectors were not the cause, and the decay was not either, since a decayed count of the same hits is the same count at any rate. Counting hits alone then left lo-fi, at 80 BPM with quiet hats over a pad, twice as busy as hardstyle at 150 with loud ones: the detectors hear its sparse quiet hats, each band being measured against its own history, and do not hear the dense loud ones. So each hit is worth how far it stands above the bed. A hat under a pad lifts the mix by a tenth or less and is worth nothing, bar the one a beat that lands while a pulse is still ringing out, which counts about half because the bed has not caught up with it. Lo-fi now reads about 20% under hardstyle and a few percent under house. The price is that hats hardly count at all, over a pad or over a kick alone, so `pace` is how many kicks, snares and other big events there are a second, and the figures this section used to give for it (a pad with a pulse about 2, a full kit with hats about 6, drum and bass past 12) no longer describe it. They were read off real tracks on a 120 Hz display through the per-frame count, which ran two to three times the true rate there, and they have not been re-measured. `PACE_FULL` went from 12 to 4 with this change, since at 12 every track sat in the bottom quarter of the range: settled, 80 BPM now reads near a third, 128 near a half and drum and bass near three quarters. That is a guess from tempo, and it wants checking against real tracks.

What `pace` still cannot do is hear a regular train of hats reliably. The onset threshold is the mean plus 2.5 deviations of a band's own last second and a half, and a train of equal hits raises both, so for a flat-topped hit that fills more than about a seventh of the time the threshold sits above every peak and nothing fires, which is probably why hardstyle's ten hats a second never reach its treble detector. A train just under that limit clears the threshold by a percent or two, and whether a frame lands on the peak decides it: lo-fi's treble band fires on 68 of its 133 hats at 60 frames a second and on all 133 at 120 and 144. The weighting keeps that out of `pace` for hats under a pad, and the worst spread measured on variants of the three tracks (other tempos, other hat levels) is 0.013, but a track of regular hats with nothing over them is where two frame rates could still part. The whole-spectrum detector, which `onset` and `beatPulse` come from, has the same trouble: on hardstyle it fires on 3 of 62 kicks at 60 frames a second and on 62 at 120.

Four more rows say where in the song we are rather than what kind of song it is: the moment. Groove has no row, because it is what is left when the other three are low, and there is no intro or outro row either: those are about where we are in the track and not about the sound, so `moment.ts` reads them from how much has been heard and, when the host gives it, the playhead. See [The director](#the-director). Every one of them is a difference between two arms of the same quantity, never a level against a fixed number, and three things follow. They are loudness independent, since a difference of dB is a ratio. They are frame-rate independent, since every arm is a span of time and the hits are counted the way `pace` counts them. And `tension` falls back by itself when a build fizzles, because a riser that climbs and then holds stops being a change within the slow arm's sixteen seconds whether or not anything notices it fizzled. The first cut read levels against the track's norms and could not do that: a track that got louder and stayed there sat at full tension for the rest of the song.

The figures below are measured on one synthesised story, in `synthetic.ts`: twenty-four seconds of four to the floor at 128, sixteen of breakdown, sixteen of the groove again, then `build()`, which is a snare roll doubling from quarters to eighths to sixteenths under a riser climbing from 200 Hz to 2.6 kHz with the kick out for the last bar, and then the drop.

- `tension`: something is winding up, over seconds. Four pieces of evidence, of which it takes the mean of the best two. The mix louder over four to sixteen seconds; the top of the spectrum climbing over the same, times whatever `harmonicChange` leaves, since a chord moving brightens a mix and is not a riser; struck sounds a second over three seconds against the same over twelve, which is a roll; and the low end falling while the top does not, which is the floor being cleared. The best two rather than all four, because a build that only rolls has no riser and one that is only a riser has no roll, and rather than the best one, because a single moving number is the first bar after any section change. Then two things cut it: the low end coming back, read over two seconds, and `release` outright. Without the first, the drums returning after a breakdown read as a build for as long as the slow arm took to catch up, which is a quarter of a minute of winding up at the moment the track has just unwound. It reads 0.71 through the synthetic build and at most 0.01 anywhere before it, 0.02 through a minute of steady house with nothing happening in it, and 0.63 through a build that fizzles, falling to 0.11 five seconds after the sweep and the roll stop. The top of the spectrum is read as the high group's own level in dB and not as the centroid `weight` uses, because the centroid is held at NaN under the -60 dB floor and a normal mix 20 dB down is under it, so every riser in a quiet listener's music went unseen.
- `release`: the payoff is happening. The low end's recent peak coming back over its own sixteen-second arm, times how wound up the last few seconds were, times a novelty weight that runs from a half to one. The split is the whole of it: the low end coming back hard is what a kick does four times a bar, so the arm carries all of the specificity and a peak follower on the low end, quick up and slow down, carries all of the speed. Measuring the return strictly enough to stand alone cannot be done inside a beat, because a mean slow enough not to swing with the bar is two seconds wide and two seconds is four beats late. The arm is weighted by how far the low end had got out from under the build, at a third for a build that keeps its kick all the way through and at full for one that empties the floor first. It then falls to 1/e over half a phrase, eight beats read off the tempo when `tempoConfidence` is at least 0.4 and three seconds when it is not. It peaks at 0.46 to 0.50 in the second after the synthetic drop, is under 0.2 one phrase later, and stays under 0.1 through everything before the build.
- `rest`: the floor has dropped away, over seconds. Loudness well under the loudest the track has lately been, where that loudest is a decayed maximum in dB that forgets a tenth of a dB a second, so a breakdown does not wash its own reference away. Three dB under is the start of it and ten dB under is the whole of it. Then half as much again from two witnesses: how thin the low end is, as the share of the span's power under 250 Hz, and how few struck sounds a second there are. It reads 0.72 at the end of the synthetic breakdown, 0.00 through the groove before it and under 0.1 eight seconds after the groove comes back, and 0.00 through steady house. It reads the raw loudness and deliberately not `energy`, which is divided by its own recent peak and so reads near 1 through a breakdown as much as through a drop.
- `impact`: an event and not a level. 1 on the frame the `release` evidence crosses 0.28 going up, then falling to 1/e in 180 ms, which is what `beatPulse` does, so a scene reads it the way it reads a hit. It rearms when it falls under 0.096, which is what makes one drop one impact however long the payoff sits at the top. A level crossing and not a rise per frame: a rise per frame is how far a signal moved in one step, which is smaller the finer the steps, and is exactly the shape of the bug `pace` had. On the synthetic story it fires once, on the same frame at 60, 120 and 144 frames a second and 20 dB down, well inside a beat of the drop (how far inside depends on where you reckon the analyser's window sits, so the test asks only for a beat); on a build that fizzles and on a minute of steady house it never fires.

What the moment is good for and what it is not. Across tension through the build, rest through the breakdown and release at the drop, the widest gap between 60, 120 and 144 frames a second is 0.04, and 20 dB down moves them by at most 0.03. What it cannot see is a build inside a track's first sixteen seconds: until the slow arms have seen a full window there is nothing behind them for a change to be a change against, so each is held at its own mid arm and every difference reads zero, the way `swell` holds its long arm for the first half minute. It also barely hears a roll past a point. Counting the sounds struck rather than the detector firings, the synthetic roll's rate rises by about a third from quarters to eighths and not at all from eighths to sixteenths: sixteenths at 128 are 117 ms apart against a 100 ms window in `hardness`, a snare rings for a quarter of a second so three of them overlap, and a train of equal hits raises the threshold of its own band. The doubling a listener hears is mostly not there to be counted, so the roll is the weakest of the four pieces of evidence and the riser and the cleared floor do most of the work.

Silence is held through and not measured. A pause, a seek and the gap between two tracks all read as exact silence, and the arms are means of dB, so stepping them through five seconds of it sank the four-second arm far enough that a groove coming back at full energy read as `rest` at a half for twenty seconds more. Under -120 dB every arm and both hit counts stay where the music left them, `rest` climbs to the top, and tension is kept: the bar of nothing some tracks put before a drop is the top of the build, and the drop after it still fires its one impact. More than eight seconds of silence is taken for the end of a track, and what follows starts again as the first track did. Arms are seeded from the loudest reading of their first second and not from their first frame, which after a gap or on a fade-in is the front edge of a sound and reads fifty dB under it. One thing still to settle on real tracks: a build that keeps its kick to the last beat arms `release` at a third, which tops out at 0.30 against the 0.35 `impact` fires at, so that drop has no impact at all.

**What is published is not the evidence itself.** Inside the estimator `tension` and `release` are levels of evidence, and neither reaches 1 on music: `impact` fires when the release evidence crosses 0.28, and on the first real track a drop peaked at 0.41 and a build at 0.49. The numbers in the bullets above are that evidence. The packet carries each against the level that means the thing is wholly happening, `TENSION_FULL` 0.5 and `RELEASE_FULL` 0.4, clamped at 1, so a consumer reads 0 to 1 and means it. On the synthetic story that is a tension of 1.00 through the build and 0.02 before it, a release of 1.00 on the drop and 0.36 a phrase later, and after a build that fizzles a tension of 0.29 with no impact. Published raw, everything downstream worked round it in its own way: the director divided the rows back up, every study written so that a tension of 1 is the whole effect ran at half strength through a real build, and the shards' gate on release shut a second after the drop. Every threshold inside the estimator is still on the evidence, which is why the scale is applied on the way out.

**These numbers are tuned on synthetic structure and have not been tried on a real track.** Every threshold in the estimator was read off the story above and off a minute of steady house, which is a fair test of whether the measures are frame-rate and loudness independent and no test at all of whether 0.71 is what a build should read on a record. Expect to move them, and expect the ones that move most to be `TENSION_RISER_DB` and `RELEASE_LOW_DB`, since both are read off a high group and a low group whose shares differ far more between genres than between frame rates. The director reads all four: `moment.ts` turns the first three into weights and `director.ts` reads `impact` the way a scene reads a hit.
A slow feature and a fast one pointing at the same knob add, so `pace → vorticity` on top of `treble → vorticity` can push a knob past what either was tuned for. The gains are the control and zero is off.

### The beat as a clock

Everything above reacts. `beatPulse` jumps when an onset has already happened, and the fastest a study can answer is a frame late. Two more rows let it anticipate.

- `beatPhase`: where in the beat we are, 0 on a beat and rising to 1 just before the next, predicted from the tracker's period and phase rather than read off an onset. Through `invert` it is a pulse that falls across the beat and lands on time; through `square` it is a ramp that gathers toward the beat. It runs on through a passage where the tempo drops to 0, at the last tempo that won, because a ramp that carries on through a bar of doubt is less jarring than one that stalls; it is 0 only before any tempo has ever been found.
- `tempoConfidence`: how well the chosen period correlates, 0 to 1. A click train reads about 0.9, four to the floor about 0.85, a two-step about 0.45, a breakdown with no drums under 0.2, and noise or silence 0. A phase on a wrong tempo is a steady rhythm in the wrong place, so a preset that maps the phase wants a second row that thins the same knob as the confidence falls, or gains that do nothing at 0.

The phase runs about a thirtieth of a beat behind the signal, since a hit has to get some way into the analyser's window before its rise shows. It is the same on every beat, so it reads as a fixed offset and not as drift.

### The harmony

Band energy knows a band is loud and nothing else. Three more rows know which notes are playing, so a song can have a colour of its own and a chord change can be seen.

A chroma is read each frame from the peaks of the log spectrum between 100 Hz and 5 kHz: a bin louder than both neighbours and above about -60 dB, its frequency refined between bins with a parabola through the neighbours (a bin is wider than a semitone below 200 Hz), folded onto its nearest of the twelve pitch classes and weighted by its log magnitude. Peaks rather than every bin because drums fill every bin: on a real track a magnitude chroma wavered between a key and its relatives while the peak-picked one held the right key throughout.

Three copies of that chroma are kept, smoothed over 0.3 s, 2 s and 8 s.

- `keyHue`: the key the 8 s chroma fits best, by correlation with the Krumhansl and Kessler profiles for the twenty-four keys, placed on the circle of fifths as a fraction of the way round: C at 0, G a twelfth on, F a twelfth back. Neighbours on the circle share most of their notes, so a modulation to the dominant is a small step of colour and a jump to a distant key a large one. A minor key sits where its relative major does, since the two are the same notes; that also keeps the profiles' habit of flipping between relatives every few bars from moving the colour. The hue is ramped over 3 s as a unit vector, so a key a full turn away is still the short way round. `keyLabel` turns it back into a name for the overlay.
- `keyClarity`: how surely that key is heard, from how well the profile fits (0.4 reads as none, 0.9 as certain) times whether anything tonal is sounding now at all, so it falls the moment the notes stop while the slow chroma still remembers them. On drums alone it sits low.
- `harmonicChange`: the cosine distance between the 0.3 s chroma and the 2 s one, times three. A chord that moves pulls the two apart for as long as the slower one takes to catch up, and then it settles, so it is a pulse of a couple of seconds with no event logic behind it. It is about which notes are sounding and not how loudly.

On Blossom (Au5, 140 BPM, F# minor) the hue read A / F#m for the whole track, the clarity 0.6 to 0.9 in the pad and breakdown passages and 0.1 to 0.5 in the drops, and the change lifted where the chords moved in the sparse passages and was drowned by the drums in the loud ones. That is the honest limit of a chroma read from an FFT: it holds the key, and it sees chords move only when the mix is thin.

### The structure

A song is a shape over minutes, and nothing above remembers more than half a minute of it. Three more rows do.

Every two seconds a snapshot is kept of what the last couple of seconds sounded like: the five band levels and energy, a hit rate per band, and the shape of the 2 s chroma (each bin less a flat twelfth, so a passage with no notes contributes nothing), 23 floats. Swell is deliberately not in it: it is loudness against the last half minute, so the same quiet passage reads differently after a drop and after silence, and with it in the vector a returning passage failed to recall itself. Every section that has ended is also kept as one mean vector. Twice a second the present is compared, by cosine, with those section means.

- `recall`: the best of those matches, mapped so a distance of 0.3 of the reach reads 0 and 0.05 of it reads 1, which on a track that reaches as far as the one this was tuned on is the similarities 0.94 and 0.99 it used to be fixed at. The section going on is not among the memories, so a steady passage does not recall its own start and a returning one recalls the whole of its first time round. Whole sections rather than the two-second snapshots, because a single snapshot of the intro's last bar matched the first drop well enough to call the drop a return of the intro. On Blossom the three drops matched one another at 1.00 and a verse its own return at 0.98 to 0.99, while a drop against the intro sat at 0.96 and against a verse at 0.94, which is why the map is that steep and sits just above those.
- `novelty`: how far the present has moved from the snapshot ten seconds ago, against the furthest this track has moved (the reach, below). It lifts for a few seconds after a passage changes and then settles. It lifts on a fill too, which is right for a level and wrong for a boundary, so a boundary takes two steps.
- `section`: which section this is, 1 for the first. Novelty at 0.4 or more, once a section has run six seconds, is a candidate, which is now 0.4 of the track's own reach rather than a fixed level; a level rather than a rising edge, because a riser running straight into a drop keeps the novelty up across both and an edge missed the drop. Six seconds on, the mean of the new passage (from a second and a half after the candidate) is set against the mean of the section it would end (from four seconds after that began, and only from moments when the novelty was low, so a riser running into a drop cannot fold the drop into its own section), and if the two are closer than 0.68 of the gap (below) the candidate was a fill and is dropped. A confirmed boundary rejoins an older section when the recall to it, judged with the closest the present has come to it while the candidate was open, reaches 0.6, and otherwise starts a new one. On Blossom that put all three drops in one section, the two risers before the second and third in another and the quiet passages mostly together, called the first drop about ten seconds late, and found a boundary or two more than a listener would count. The lateness is the price of confirming: a change is only a section once six seconds of it have been heard, and a change that follows another within six seconds waits its turn, so a riser that runs straight into a drop can put the drop's layout ten seconds behind the drop. The novelty level lifts within a second or two either way, and that is what the studies turn into the surge; the layout is the slower confirmation. It is an id rather than a level, so it is not in the mapping vocabulary; the fluid reads it straight from the packet, the way it reads an onset, and chooses a layout with it. That is what lets a chorus that comes back come back to the same look.

**Nothing above is a fixed amount of difference, because how far apart a track's passages get is a property of the track.** Everything else the extractor measures is already relative to the track's own recent history: the onset detectors keep a rolling mean and deviation, the band levels are scaled by the loudest that band has lately been. Novelty was the exception, a fixed gain of five and a fixed bar of 0.4, and both were read off one dance track. Measured over two minutes of Bring Me The Horizon's Antivist at full volume, the cosine distance between the present and ten seconds ago peaked at 0.080 where the demo's own track reaches 0.223, so the novelty row peaked at 0.36, never came near 0.4, and the whole track was one section and one cast. That is what "every metal song looks the same" was.

Two scales replace the fixed ones, both of them the largest this track has shown rather than a window of it, since they say what kind of track this is and not what just happened. A scale that fell back between two drops would lower the bar for a candidate and tighten the test that throws fills out at the same time, which is the wrong way round.

- The **reach** is the furthest this track has put two moments ten seconds apart, which is the size of the change a boundary is made of. `novelty` is the distance against it, so the row means the same thing on any track: 1 is the biggest change this track makes. The candidate bar stays 0.4 and is now 0.4 of the reach. It is clamped between 0.05 and 0.2: 0.2 is where the old fixed gain of five put full scale, so a track that already reaches that far reads exactly as it did and the worst a freak moment can do is put a track back to today's behaviour, and 0.05 is four times the 0.013 a steady synthetic passage wanders by, so a passage going nowhere cannot be stretched into structure. For the first thirty seconds the reach is held at full, so that the first change heard cannot set the scale by itself; thirty seconds is what it took all four tracks measured to show their widest change.
- The **gap** is the furthest a six-second window of the track has sat from its section's mean, and the confirmation is a share of it rather than of the reach. The confirmation compares two means and not two moments, and means of a dense track converge on each other: a candidate's mean on Antivist sits 0.001 to 0.016 from the section it would end and the whole of its gap is 0.011, where the demo track's sits 0.017 to 0.158 and its gap is the full 0.054. As a share of the reach the two tracks' fills and boundaries overlap and no one bar separates them; as a share of the gap, over the four tracks and the synthetic story, every fill sat at 0.65 or under and every boundary at 0.71 or over, so the bar is 0.68 and it sits between them. Six seconds because that is the span a candidate's own mean covers, so the yardstick is the same quantity the test is. Its floor of 0.008 is the guard a share cannot give itself: a steady passage's window never got further than 0.003 from its own mean, so its gap sits on the floor.

The published `novelty` row is the relative one, not the raw distance, so every reader gets the fix and not just the candidate test. The director reads it at 0.4 as a fast signal ahead of a confirmed section, `release` weighs a drop by it, and the studies map it to force: on a track whose raw novelty tops out at 0.36 all three were as good as dead, and none of them wants a distance in the first place, they want how big a change this is for this track. The three constants that read it (`NOVELTY_ON` and `NOVELTY_OFF` in the director, `RELEASE_NOVELTY_FLOOR` in the moment) are unchanged and mean what they did, since a track that reaches the full reach reads exactly as it did.

`recall` is on the reach too, for the same reason: on a dense track every passage is 0.94 to 0.999 similar to every other, so a fixed map reads every one of them as a return and a metal track would rejoin its way back to one section from the other direction.

The three that worked keep what they had, to the second and at 60 and at 144 frames a second, bar Daft Punk's one boundary being called seven seconds earlier: that is the point of holding both scales at what a dance track reaches until a track shows it is denser. Live in headless Edge on a real GPU, playing Antivist at full volume through the demo's file input, the novelty row peaked at 0.34 with no section change before and at 0.82 with five in the same two minutes after, and the demo's own track kept its boundaries at 28s and 54s either way. The synthetic dense song in `synthetic.ts` is the case in a test: a verse, a chorus and the verse again, a wall of noise with a kit over it, loud from end to end and differing in a couple of bands and in how busy the kit is. Its novelty peaked at 0.24 under the fixed gain, and 0.12 at 144 frames a second, and it was one section either way; it now finds both boundaries, rejoins the verse, and finds nothing in ninety seconds of one passage.

**The scales belong to one play of one track.** Both are the most the track has done so far, so two things that are not the track doing anything have to be kept out of them. A seek: the present against ten seconds ago is then one part of the song against another, the widest change the extractor ever sees, and taken as the track's reach it pins the scale at the top for the rest of the play, which on a dense track is the fixed bar back and no section after the first drag of the playhead. So the renderer watches the `playhead` a host gives, and when it moves by more than a second and a half against the frame clock it tells the extractor (`seeked`), which starts both scales over and takes nothing into them for eighteen seconds, until the jump has left the lag and been confirmed as a boundary. And the song before: when `track` changes the extractor is built again, so a dance track's wide scale, its sections and its tempo are not the next song's past. A host that gives no `playhead` cannot be watched for seeks, and one that gives no `track` has every song read against the first.

What this does not fix. Where a boundary is called is still frame rate dependent, and was before: the demo track finds four boundaries at 60 frames a second and five at 144, and The Terminal eight and nine, unchanged by any of this. The structure vector counts a band's hits per frame, which is the same thing that made `pace` read the display before it was fixed, so a faster display reads a slightly different vector and the marginal decisions land differently. It shows most on the dense song, where the passages sit so close together that most decisions are marginal: Antivist finds five boundaries at 60 frames a second and seven at 144. The vector itself is the deeper limit. On dense music the band levels are pinned near the top of their range by their own peak scaling, the chroma of a wall of distortion is nearly flat, and what is left to tell a verse from a chorus is the hit rates and a little of the tilt.

Nothing is remembered until the vector has had four seconds to settle, and once the notes have faded the chroma reads as flat rather than as the last note held for ever, or a memory of the cold start would read as a boundary against everything.

### The renderer

`src/gpu/Device.ts` shares one device and any pending acquisition across callers. Acquisition makes up to three attempts: first with the high-performance preference, then with the browser default after waits of 300 ms and 600 ms. Request exceptions and uncaptured GPU errors are logged. Device loss clears the singleton so recovery can request another device. Recognised software adapters use reduced budgets.

`src/gpu/Renderer.ts` is the one renderer, and it draws a cast rather than a scene: one a host pinned, or one the director is choosing. It owns that director and steps it once a frame. A stage hands it a canvas on mount and takes it back on unmount, which matters because a host may portal the stage into another document (Musimo's popout does) and the subtree then remounts on every move:

```
module singleton, survives remounts        per mount, made again each time
----------------------------------        -------------------------------
GPUDevice, CPU feature packet              canvas elements (scene + HUD)
one implementation per live study,         GPUCanvasContext, configure()
  with its pipelines and its textures      ResizeObserver, visibility hook
the post stack and its parameters          requestAnimationFrame handle
the cast, what is live of it, and the
  object the studies layer resolves into
the flow blend target
the feature worker and its client
frame clock, HUD history
```

The post stack's offscreen textures belong to neither column: the singleton owns them and rebuilds them whenever the canvas size changes. The renderer always forwards the current dimensions to every implementation, even if the canvas size is unchanged. This matters when a fresh one is built on an existing canvas; otherwise its internal dimensions can remain 1×1.

`attach` configures the context, sizes the canvas to its CSS box times `devicePixelRatio`, and starts a loop on the canvas's own window, so a popped-out window keeps drawing while the tab behind it is hidden. On device loss the renderer drops every implementation, the post stack and the feature client, then reattaches the same canvas through the bounded acquisition retries. Startup, recovery and frame errors are logged and reach the fallback. A failed frame cancels the next animation callback instead of submitting repeatedly. `VisualizerStage` ignores inactive callbacks and replaces its scene canvas once after failed recovery, allowing a different graphics backend. If graphics remain unavailable, Retry graphics retains audio playback.

Each frame, in order:

```
read the analyser, stamp time and dt into the packet
step the director with the packet and the real dt
  -> what is live, and the fade each of them is at
     (with a cast pinned it is stepped anyway, and that cast is drawn)
reconcile what is built, but only if the set of live ids moved
age what is held spare, and release anything out of its grace
resolve what is live into a set of knobs per study id and the whole post stack
update every flow, then every ink        (flows first: a dye ink's numbers
                                          reach the solver through its flow.
                                          two studies of one flow are stepped
                                          once, knobs blended by presence)
simulate every flow into the encoder
blend their velocity fields into one     (skipped when one flow is live)
write the post uniform
clear the shared target
render every ink into it, in cast order  (the ribbon's pass among them)
run the post stack onto the canvas
draw the HUD if it is on
```

Each implementation uploads its own resolved numbers. Nothing per frame touches React, and nothing per frame allocates: the director hands back one list of the same entries every frame and moves the presences in place, so the split by kind and the reconcile below happen only on a frame where the ids themselves moved, and the studies layer writes into one object the renderer keeps.

What is built is reconciled in `syncImpls`. A study that has left hands its implementation to one that wants the same one rather than having it torn down, so Plume to Melt keeps the field the fluid has already stirred and only the numbers change. Three rules hold it together:

- **Nothing is torn down on the frame its study left.** An implementation nothing is asking for is held for six seconds and released after that. The change most likely to ask for one straight back is a novelty spike fading a cast out and the confirmed section, about six seconds behind the music, settling it back again; holding for that long makes the round trip a fade of the numbers rather than a rebuild.
- **Only a change of pinned cast empties the canvas**, the way changing scene always did. Under the director it never does: a section change would build the incoming ink, blacking the picture out, and a few seconds later release the outgoing one and black it out again, so every glide would pop twice. The whole point of one canvas is that a change of cast morphs what is already on it.
- **Two live studies of one implementation run as one.** Flows are keyed by implementation rather than by study id, so a fade from `lazy-fluid` to `turbulent-fluid`, which is one solver at two sets of numbers, steps one solver and walks its knobs from one study's to the other's with `blendKnobs`. The dye is bound to that solver, so it carries across the fade untouched. `impls/FlowBlend.ts` is for two flows of genuinely different implementations, which nothing in the registry is yet.

A study whose implementation this renderer has nothing for is skipped and the cast draws with what is left, which is how the WebGL2 path works: the fractal is the only ink there. A cast the director chose may hold no fractal at all, and a song is not worth stopping for that, so the default pinned preset stands in, or the first shipped cast that path can draw when the default is not one, which is Prism. A cast a host pinned is left alone, so pinning one the fallback cannot draw still reaches `onUnsupported`. Construction stays in the renderer so every implementation shares one device and one post stack, and so nothing in the studies layer has to import a shader.

The flows are stirred before the inks draw, so the picture is carried along the field this frame solved rather than the last one's, and each field is read after its own `simulate` because the half of a ping-pong pair it names alternates. Two flows are live only in the middle of a change the director is running, and `impls/FlowBlend.ts` sums them into one field weighted by presence and normalised, so two at a half each carry the picture as far as either alone. With one live flow the pass is not encoded at all.

### Implementations

Behind each `impl` id in `src/studies/impls.ts` there is one GPU object, and `src/scenes/Impl.ts` beside `Scene.ts` is the two shapes they take. Both share `init`, `resize`, `update` and `dispose`, and a `detail` line naming what they are doing, empty when there is nothing to add.

```
FlowImpl                             InkImpl
simulate(encoder)                    render(encoder, view)
flow: the field it just wrote        maxFps, maxPixels: its budgets
```

Both are handed a `presence`, 0 to 1, with their knobs. At 0 a study is not in the live list at all, so nothing is resolved, no pass is encoded, no buffer is uploaded and, unless something else needs it, no object is constructed. Between 0 and 1 an ink scales its light and a flow scales its velocity, and what that means is the implementation's business, because thinning a fluid is not the same operation as thinning a line.

| `impl`     | What draws it                       | Kind |
| ---------- | ----------------------------------- | ---- |
| `fluid`    | `impls/fluid.ts`, `FluidFlow`       | flow |
| `analytic` | `impls/analytic.ts`, `AnalyticFlow` | flow |
| `dye`      | `impls/fluid.ts`, `DyeInk`          | ink  |
| `fractal`  | `scenes/Kaleidoscope.ts`            | ink  |
| `ribbon`   | `impls/RibbonInk.ts`                | ink  |
| `streaks`  | `impls/StreaksInk.ts`               | ink  |
| `shards`   | `impls/ShardsInk.ts`                | ink  |
| `dust`     | `impls/DustInk.ts`                  | ink  |
| `caustics` | `impls/CausticsInk.ts`              | ink  |
| `halo`     | `impls/HaloInk.ts`                  | ink  |
| `rings`    | `impls/RingsInk.ts`                 | ink  |
| `spectrum` | `impls/SpectrumInk.ts`              | ink  |
| `sparks`   | `impls/SparksInk.ts`                | ink  |
| `look`     | nothing; a look is `PostParams`     | look |

**Every ink adds light.** The renderer clears the shared target once a frame and each ink then draws over what is there, blended as its own colour times the presence, with the alpha left where the clear put it (`INK_BLEND`). For one ink at presence 1 that is exactly the opaque draw each of them used to make on its own, which is why the five look as they did. They draw in cast order, so a cast reads the same way every time.

**The fluid is one object split between two studies.** `Fluid.ts` owns the field; `simulate` is the solve and `drawDye` is the dye drawn out of it. The split cannot be two objects, because one splat carries both an impulse and a puff of dye, written by the same compute step out of the same uniform, so `fluidTuning` in `fluid.params.ts` is where a flow's knobs and an ink's meet. That is why the dye study carries `requires: ['fluid']`: without a fluid flow in the cast there is no field for it to draw, and the renderer builds it against the flow that is already live. With no dye ink on it the ink's knobs are simply absent and the fluid falls back to its own defaults, which is what a flow under another ink was always handed. Presence scales `force`, `hitForce` and `eventForce` and nothing else: the field has momentum, so a fade reads as the current easing off rather than the picture stopping dead.

**The analytic flow is a velocity you can write down.** About a dozen of the flows in the catalogue are not simulations at all: implode, radial burst, tunnel, vortex, polar twist, shear bands, ripple, lattice warp, drip, curl drift. Each of them is a function of position and time, so they share one implementation and a study on it is nothing but numbers. `impls/analytic.ts` writes one fragment pass into a 128 texel square `rgba16float` field, in the same units and through the same `cover` the fluid's field uses, and the maths is in `impls/analytic.params.ts` with the shader as a line-for-line transcription of it. See "Adding a study" below for how a term is added.

**A flow offers its field** as a texture view, the `cover` that maps canvas uv to that field's own uv, and its size. The feedback pass reads the last frame back along it, which is `feedback.carry` under Post stack below; with no flow live the stack binds one zero texel in its place.

**The ribbon's pass belongs to the post stack** and is encoded by the ink. The line reads the same uniform every post pass does and its points buffer is made once at start-up, so moving the pass out would mean a second uniform saying the same things; what the ink owns is when it runs, which is its place in the cast's ink order. Its presence is applied by the studies resolver instead, since the stack knows nothing of presence.

**No implementation decides what drives what.** `update` takes the packet and a set of already resolved numbers, and every magnitude comes from the second of those; the packet is read for the clock and for events such as an onset. Per-band levels and hits are the exception. The fluid's voices and the fractal's band envelopes read them straight from the packet, so a study scales them with a knob such as `bandReaction` and cannot remap them.

#### The fractal

The demo defaults to **Prism**. **full view (F)** fills the browser while music continues. **Esc** returns to controls; **H** toggles the HUD. The default track is Ecstasy Of Soul. A local, Git-ignored `demo/public/audio/Ecstasy Of Soul.flac` is tried first, with `Ecstasy Of Soul.m4a` as fallback. The original M4A is unchanged. Both files are Git-ignored, so a fresh checkout or worktree has neither; the demo then asks for a track and stays black until one is dropped in. FLAC playback avoided the media crashes seen during testing. To create that local copy, run `ffmpeg -i "Ecstasy Of Soul.m4a" "Ecstasy Of Soul.flac"` in the audio directory, or choose another track.

`src/scenes/Kaleidoscope.ts` is the `fractal` ink and draws the 3D fractal in `src/shaders/kaleidoscope.wgsl`. The WebGL2 path uses `KaleidoscopeWebGL.ts` and the matching `kaleidoscope.glsl`, with the same CPU band processing, mappings and motion. Rays march through mirrored box and sphere folds. Surface normals, coloured materials and highlights give the nested forms depth. The distance estimate uses reduced steps and a fixed budget; it is not a proven conservative bound for every warped configuration.

The same five band envelopes and individual hits the dye uses control successive recursion scales, from coarse sub and bass structure to finer mid and treble detail. Each band controls its material contribution and influences its assigned folds. Those folds share one field, so their geometric effects can interact. Low-band hit envelopes linger longer; treble accents release faster. Hit width is not used. Silent bands contribute no material, and a silent packet renders black. `bandReaction` sets overall response strength; the study's slower mapping rows handle key, pace and harmony.

`zoom` sets base magnification. `zoomAmount` and `zoomSpeed` control the continuous inward/outward sweep, which changes camera distance and field of view. Setting amount to zero removes the sweep; zero speed holds its current phase. `symmetry` sets rotational repeats with mirrored half-wedges. `complexity` ranges from 3 to 10 and produces `complexity + 2` fold iterations. Software adapters cap complexity at 5, giving at most 7 iterations. The march stops after at most 72 steps, or 44 on software adapters. The ink sets `maxFps` to 60, so the renderer skips display frames it does not need: a 176 Hz display draws at 59 and a 144 Hz one at 72. It also sets `maxPixels` to 2560×1440, and the renderer takes the lowest of the live inks'. On a larger canvas the inks and the post stack run at that budget and the composite scales the result up, which works because every post stage samples by uv. `data-detail` reports the size actually drawn. The fluid sets neither.

**`glint` and `glintKnee` are the brightness threshold**, and they are what make this ink a glint rather than a full-frame image. The fractal covers the frame. On a canvas with no history that is fine, and Prism has drawn it that way from the start; on a canvas that keeps 93 percent of itself every frame it is not, because light that covers every pixel is summed by the trail until the whole frame sits at the ceiling. That is why Melt washed out on a drop. `glint` is the share of the frame's own brightest that the ink's light has to clear to be drawn at all, 0 for no threshold, and `glintKnee` is how soft that edge is as a share of the level, so the contour does not crawl as the fractal marches through its own folds. The whole colour is scaled by the one number rather than each channel being limited, for the reason the Tonemap bullet gives: a per-channel limit pulls the three together and bleaches the light toward white.

What the level is measured against is the decision, and it is not an absolute. The fractal's light swings with the music, so a fixed level would take a loud frame whole, which is exactly where it has to be sparse, and take a quiet one to black, where there was nothing wrong. Instead the level is `glint × GLINT_CUT × intensity × 2.2 × drive`, worked out on the CPU in `scenes/kaleidoscope.params.ts`: `intensity` and the shader's fixed 2.2 are what scale the ink's light, and `drive` is the loudest band's own gain, clamped where the shader's mix weight clamps, which is the factor the brightest pixel of the frame is scaled by. `GLINT_CUT` is 0.2, measured: rendered on its own at a full packet, the brightest pixel of the frame sat between 0.51 and 0.68 of that reference over the whole zoom sweep and the body of the lit frame sat under 0.2 of it, so 0.2 is the top of the body and the knob spends its range there. The CPU writes the finished level into the last two floats of the uniform, so the shader's share is a dot product, a smoothstep and a multiply, and the uniform is the same 160 bytes it always was. Measured at 1280 by 720, `data-frame-ms` did not move: 13.3 to 13.6 ms with the threshold on, against 13.3 to 14.3 ms before it existed.

What it does not measure against is how much of the frame the fractal is covering, because the CPU cannot know that: it follows the zoom sweep. At the sweep's inward extreme the camera is inside the fold and nearly every pixel is a fully lit surface, and a threshold on brightness thins that frame rather than making it sparse. Measured on the adapter at a full packet, the ink lights 22.8 percent of the frame there at the knob Fractal glints reaches, against 83.6 percent with the threshold off, and 4 percent at the outward extreme. The same knob covers 73.4 percent of a loud frame and 72.9 percent of the same frame at a quarter of the level, which is the evidence that measuring against the drive does what it is there for. `kaleidoscope.params.test.ts` holds the pure `glintSurvival` to those two frames, binned and kept.

`depth` changes the twist through the volume; `warp`, `thickness` and `bassLift` adjust fold geometry. `bassLift` only widens the coarsest folds, by under one percent at full value. Fractal glints leaves it at zero and maps nothing to it, so it does nothing there. `sparkle` adjusts treble highlights. Rotation, travel and morph speeds preserve their phase when changed. Intensity and palette controls apply after material shading. Parameter limits also apply after audio mapping.

Material detail is filtered against an estimated pixel footprint. Surface normals get the same treatment. The march uses every fold, because the surface is defined by them. The normal is taken from a copy of the distance field in which folds with creases smaller than a pixel fade out (`LOD_LOW` and `LOD_HIGH` in the shader). Left in, those folds gave each pixel a near-random normal that flipped between frames, which was the fine-detail shimmer. The pixel size used for this and for the hit test follows the zoom sweep's field of view. Hardware rendering takes four spatial samples below 900 pixels on the shorter side, two from there up to 3.6 million pixels, and one above that. Software rendering takes one sample. Both paths upload the same 160-byte uniform block. Prism is shown through Clean glass, which is bloom and tonemapping; grain and chromatic splitting are off, and its canvas is off too. WebGL post-processing uses float HDR targets where supported, otherwise RGBA8, which clips bright values before tonemapping. Software WebGL limits the drawing to approximately 480×270 pixels in area and a maximum dimension of 960, while the HUD stays at display resolution. This keeps CPU rendering usable at lower fidelity and performance than GPU rendering.

Native GPU checks rendered all five isolated bands, exact black silence, a quieter mix and both tested zoom values (0.4 and 1.9). Five shader-only timing samples measured 6.09–6.68 ms at 1920×1080 and 12.39–13.57 ms at 3840×2160 on the development GPU. These exclude the post stack and browser, and do not establish sustained frame rates or performance on other GPUs. A 12-second, 960×540, 30 fps preview of the track's 45–57 second segment reused the repository's FFT, feature extractor, motion, mappings and full post stack. Native GPU validation and complete video decoding passed.

The external Chromium browser was verified using a real NVIDIA Blackwell WebGPU adapter at 1412×1020, with a visible fractal and positive music-band readings. All 197 tests, typecheck, lint, formatting and production build pass. Its scene initially reported 1×1 despite a full-size canvas; forwarding dimensions to every new implementation corrected that mismatch. A brief HUD reading is not a sustained performance benchmark. Separately, the in-app browser's software WebGL2 path passed reload/playback, seek, zoom 0.4 and 3, reset, full-view round trip and pause-to-black checks. Fresh-canvas recovery has regression coverage, but device loss was not exercised end to end. Against a 16-sample reference at 1037×947, the normal fix cut disagreeing pixels from about 14% to 5% in a lighting-only view, and the full picture measured about 0.5 to 1.3%. On an RTX 5080 at 176 Hz, the frame cap took GPU use from 55–99% to 23–39% and power from about 200 W to 110 W. One sample per pixel was tried and kept at two, since edge error rose from 1.3% to 3.5%. A 4380×2160 canvas pinned the same GPU at 99%; the pixel budget, with one sample per pixel at that size, brought it to about 60% at a steady 60 frames a second. Whole-track tuning and Colin's acceptance against the references remain open. See [the research and plan](docs/kaleidoscope-research-plan.md).

#### The fluid

`src/scenes/Fluid.ts` with `shaders/fluid.*.wgsl` and the numbers in `scenes/fluid.params.ts`. Stam's stable fluids on a square grid of compute textures, one entry point per step, all dispatched inside a single compute pass because dispatches in one pass are ordered and see each other's writes. The solve is the `fluid` flow and the draw is the `dye` ink, split as Implementations above describes:

```
advect velocity ─► diffuse xN ─► curl ─► vorticity and injection ─► divergence
                                                                       │
      draw ◄─ advect dye ◄─ subtract gradient ◄─ pressure xN ◄─ relax ◄─┘
```

Velocity is kept in grid widths per second, so a semi-Lagrangian backtrace is `uv - velocity * dt` with nothing scaling in between. The pressure solve is 24 Jacobi sweeps warm-started from last frame's solution faded to 0.8, which converges far better in that many sweeps than starting from nothing. The viscosity solve is two sweeps with the alpha set directly rather than derived from a physical viscosity, because what is wanted is a knob. Walls are free slip. Vorticity confinement pushes each eddy back toward its own centre, which keeps small detail alive against the smearing advection adds.

Every field is `rgba16float`, including the three carrying one number. `r32float` would halve the memory but is not filterable, so each would need its own bind group layout; one format means one explicit layout and any three fields can go to any step. Curl is read before divergence is written, so both live in one scratch field. Seven textures in all: velocity, dye and pressure ping-ponging, and the scratch. 14 MB at 512, 56 MB at 1024. A cast whose flow is a fluid with no dye ink on it pays the same, since the field is there whether or not anything draws it; Melt at 512 is 14 MB on top of what the fractal and the stack hold. Two flows live at once, which only happens in the middle of a change the director is running, are two fields and a blend target.

The grid is fixed at 512 or 1024, so nothing is rebuilt on a resize. It covers the canvas and the overflow is cropped, which keeps the scale the same on both axes so a round splat stays round; `visibleExtent` reports the band the canvas shows and the emitters are placed inside it. A software rasteriser gets 512 whatever was chosen, with 8 pressure sweeps and one viscosity sweep.

Twenty-two numbers are what a cast moves, fourteen of them the flow's and eight the ink's: the two decays, vorticity and viscosity, the emitters' count, spread and orbit, what they trickle, what one onset adds on top, where the dye sits in the palette and how much of its colour is kept, how far each emitter stands for a band of its own, and the five that shape the event pool below. The emitters ride a figure, evenly spaced around it, and push along the tangent of their own path; which figure is the section's, below. `emitters` is a count rather than a magnitude, so it is rounded and clamped between one and the five slots the shader's splat array holds, one per band; the uniform is always sized for all five and carries how many of them this frame filled, which is why the count can move on a slider with no pipeline rebuilt. The trickle is scaled by the step so it does not depend on the frame rate, because a track with long quiet passages otherwise settles into a still frame.

Colour comes from a 256-texel lookup table built on the CPU: deep blue through teal and green into warm orange and magenta and back to the first colour, so the coordinate wraps with no seam. The dye carries its place in that table as a unit vector rather than a number, so two plumes that meet average their colours the short way round instead of sweeping the whole palette between them. The pass that draws it turns the angle back with `fract` rather than by adding half a turn: the half turn had put every colour half a palette from where the ink asked for it, which nothing noticed while the palette drifted and everything would now that a colour means something. Saturation pulls the tint toward its own grey before it is scaled, so a passage with no key to speak of can be drawn with less colour than one that has. Density is bent through `1 - exp(-d)` before it is coloured, so a thick plume reads as its own colour rather than a flat white mass.

The numbers were set by eye at 3840 by 2160 against real tracks, and the first cut was wrong in a way worth keeping. The viscosity alpha started between 0.4 and 2.0, which at 120 frames a second is a box blur of the neighbours every frame: 4K showed enormous soft blobs with no structure in them. Dropping it to between 0.02 and 0.2, halving the splat radius and roughly doubling the vorticity turned the same passage into plumes with filaments down to a texel. Emitter spread then went the other way twice: wide enough to reach the corners left three separate plumes with black between them, so it settled between the two.

Each emitter stands for one band, as far as the `voice` knob asks it to. There are five bands and so at most five emitters; which bands an emitter covers is the fluid's own shape rather than a study's, and it comes from a table indexed by the emitter count. Every band is heard at any count, once and only once, so the knob is safe to drag:

| Emitters | What each one covers               |
| -------- | ---------------------------------- |
| 5        | sub, bass, lowMid, highMid, treble |
| 4        | sub, bass, lowMid, highMid+treble  |
| 3        | sub+bass, lowMid, highMid+treble   |
| 2        | sub+bass+lowMid, highMid+treble    |
| 1        | the whole spectrum                 |

The low bands merge first, because the ear separates the top of the spectrum more finely than the bottom and the treble is the part worth keeping on its own. A group's level and hit are the loudest of its members, not the mean: a group stands for "is any of this playing", and a mean would let one busy band be hidden by its quiet neighbours.

That band's level scales what its emitter trickles, and that band's own onset is what makes it hit. This is the part that needed the per-band detectors: with one global onset a kick and a hat were the same event arriving at two volumes, and the best the fluid could do was scale it by each band's level. Now the sub emitter fires on the kick and the treble emitter does not, because they are different events.

The group's place in the spectrum also sets the emitter's colour, how fat it is and how fast it rides the orbit: the start of the tint span, fat and slow for the sub; its end, small and quick for the treble. The tints span under half the palette on purpose. The song's key moves the whole set through `colourShift`, and that is the colour a viewer sees, with the bands as shades within it; spread over the whole palette the bands cancelled the key and every song showed every colour. `voice` at 0 puts every emitter back on the global onset and the shared numbers, which is what the fluid did before any of this; at 1 each one is only its own band.

#### Layouts

A song moves the numbers above all the time. The one thing that changes the composition is the layout: which figure the emitters ride, how far out, how fast, how the figure is turned and how bunched the emitters are along it. There are six, in `fluid.params.ts`: the Lissajous figure the fluid has always had, a ring, a figure of eight, a three-lobed sweep, a tall eight and a low wide ellipse. Which one is drawn is the song's section's: the fluid reads `section` straight from the packet, keeps the ids in the order it first saw them, and gives the first distinct section the first layout, the second the second, and a section that comes back the layout it had. A change glides over four seconds, an ease in and out between where the emitters were on the old figure and where they are on the new, so nothing jumps; the offset is bent toward a reach of 0.78 of the way to the edge, whatever the spread and the layout add up to, so a loud passage opens the figure out and no emitter ever sits on the wall. It used to be clamped at the edge itself, and since the shipped presets reach a spread of 1 in a drop, every emitter ended up pinned there with its dye piling along the wall. The rest of the section's arrival is the studies': `novelty` is a feature like any other, and the shipped ones turn it into a surge of force and dye.

#### Events

Five emitters can say which part of the spectrum is playing; they cannot single out a sound. Behind the bed sits a pool of thirty-two short-lived emitters, one spawned for every band hit, so a kick, a hat and a note each get a splat of their own. Where one lands is under its band's emitter, at the height its pitch puts it: the hit's place across the spectrum, low sounds at the bottom of the frame and high ones at the top. How fat it is comes from its band and from how wide the hit was, so a kick is a fat low puff and a hat a small high flick. Each lives for `eventLife` seconds and fades on a curve that is steep at the start and gone at the end, so a hit reads as a hit and not a glow; `eventForce` and `eventDye` are what a full-strength one adds over its whole life, whatever the life and the frame rate, so the knobs mean the same at 60 frames a second as at 144. `events` is how many may be alive at once, up to the pool, and 0 is off; when the pool is full a new hit takes the slot of the one nearest its end, so a busy passage keeps the newest sounds on screen. The splat array in the shader holds the bed and the whole pool, thirty-seven slots, and the uniform is always sized for all of them; the frame time did not move when they were added.

What this cannot do is tell a vocal from a lead synth in the same range. Two sounds that share a band and a pitch get one splat between them; that is source separation, a different order of problem.

The two sizes are not just detail levels. 512 fills the frame with bold, soft-edged plumes; 1024 draws finer, wispier ones, because the same emitter radius is a smaller fraction of the larger grid.

#### The analytic flow

`src/impls/analytic.ts` with `shaders/analytic.field.wgsl` and the numbers in `impls/analytic.params.ts`. One fragment pass, no compute, no state: the field is a pure function of this frame's knobs, so there is nothing to warm up, nothing to reset and nothing that could depend on the frame rate. The velocity is per second, exactly as the fluid's is, and the feedback pass multiplies by the real step.

The field is the SUM of a fixed set of terms, each scaled by one coefficient:

| Knob        | The term                                                                                                                                                                                          |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `radial`    | speed along the line to the centre, in field widths a second at the peak of the profile. Negative pulls in (implode, tunnel), positive pushes out (burst).                                        |
| `falloff`   | where along that line the speed peaks. 0 is speed proportional to radius, a plain zoom about the middle; above 1 the peak is `1 / falloff` of the way to the corner and the rim is left standing. |
| `swirl`     | turns a second about the centre, the same at every radius, so the picture turns without shearing (vortex).                                                                                        |
| `twist`     | turns a second added at the centre alone and gone by the corner, so the middle outruns the rim and the picture winds into a spiral (polar twist).                                                 |
| `curl`      | the speed of a drifting, folding noise that neither gathers the picture nor thins it, in field widths a second at the fastest a point goes. 0 is off and costs nothing (curl drift).              |
| `curlScale` | how many cells the noise has across the canvas's longer side. A shape, so presence leaves it alone.                                                                                               |
| `curlRate`  | how fast the pattern itself evolves, in turns a second of its slowest part. A shape as well.                                                                                                      |

`radial` is divided by the most the shape reaches inside the canvas, so it always means the speed at the peak whatever `falloff` is doing. Without that, a study driving the two from different rows would find each row changing what the other meant. Both rotations are signed, and positive is clockwise on screen, because a texture's y runs down.

Presence scales every coefficient and leaves `falloff` alone: a shape faded toward zero would turn a burst into a zoom on the way in. With every coefficient at zero, which is what implode at a tension of zero is, no pass is encoded, no buffer is written and no field is offered, so the stack binds its own zero texel and the study genuinely costs nothing until it has something to say.

The grid is 128 texels square and does not follow the canvas, so nothing is rebuilt on a resize; it covers the canvas with the overflow cropped, exactly as the fluid's does, which is what keeps one field width one canvas width on both axes so that "the centre" and "a ring" mean the same thing on a wide canvas and a tall one. 128 is enough because every term is smooth and the sampler reads it back with linear filtering: a 16 by 9 canvas sees 128 by 72 texels of it, and the sharpest thing in the field is the turn of direction around the centre, which the profile takes to zero anyway. It costs 16384 fragment invocations and 128 KB, against the fluid's nine dispatches and 14 MB.

The fluid and this can be live at once, which is what the middle of a change between them is. `impls/FlowBlend.ts` sums them by presence, and `blendTarget` takes the LARGEST of their grids rather than the first: the blend shader samples by uv, so a 128 field lands correctly in a 1024 target, but a 1024 fluid written into a 128 target would spend the whole change at a sixty-fourth of its resolution. Every flow's `cover` comes from the canvas alone, so the two share it.

**The curl term is the curl of a scalar potential**, which is why it cannot pile the picture up or thin it out: the divergence of a curl is zero for any potential, and `analytic.params.test.ts` takes the divergence by finite differences to say so. The potential is three octaves of sines, cells `1 / curlScale` of the field on a side at the base octave and half that and a quarter at the others, at 0, 60 and 120 degrees so the lattices do not line up, weighted 0.55, 0.3 and 0.15. The curl is taken by hand, which comes out as two plane waves an octave pushing perpendicular to themselves: two sines an octave, no texture to fetch, no lattice to hash and no finite difference to leave a seam. Value noise would look the same for a table and a few fetches an octave; sines repeat, and what stops that mattering is that all six waves turn at different rates, so the pattern comes back to itself only after 16 turns of its clock, 320 seconds at the resting rate.

`curl` is a ceiling on the speed of every point, since the weights sum to 1, and the RMS speed is 0.46 of it whatever the scale, so a study sets the speed and the size from two rows without either moving the other. The cells are square on any canvas, because the field is square and covers the canvas with one field width equal to the longer side, so `curlScale` is cells across that side and a cell is as wide as it is tall on a wide canvas and a tall one; a test takes the change in velocity over one pixel across and one pixel down, on 16:9, 9:16 and square, and holds the two within two percent of each other. The top of the scale range is 8 because that puts the finest wave at 5.7 texels of the 128 the field has.

Its clock is the one thing the flow keeps between frames. `update` adds `curlRate` times the real step to it, so the same seconds make the same pattern at 60 and at 144 frames a second, and because it adds up the rate rather than multiplying the total time by it, a study that moves `curlRate` with the music never makes the pattern jump. It wraps at the repeat, and it runs whether or not the curl is on, so a build that brings the curl in finds the pattern where the seconds have left it. The shader branches on the uniform, so a flow whose `curl` is 0 pays for no sines at all, and with nothing else moving no pass is encoded.

Checked on a real adapter (Edge, headless, NVIDIA GeForce RTX 5080): the shader compiled with no messages and no validation errors, and five configurations drawn into a 128 texel `rgba16float` field (curl alone at scales 0.5, 3.5 and 8 on wide and tall canvases, all four terms together, and a curl of 0 among the others) read back within 0.08 percent of the TypeScript at every texel, which is half float rounding. A pass costs about 2.5 microseconds at that size with or without the curl, best of seven runs of 4000 in one submission, which is the pass's own overhead and says only that nothing came near a budget; statically the curl branch is about 30 instructions an octave, two of them sines.

Adding a term is three things: its coefficient in `ANALYTIC_KNOBS` (`presets/knobs.ts`) with a range in `ANALYTIC_RANGES`, a field of `AnalyticField` written into a vec4 of its own by `writeAnalyticUniform`, appended after the vec4s that are already there so nothing moves, and the same few lines in `analyticVelocity` and, transcribed, in the shader. The WGSL struct is one vec4 per term family for exactly that reason. A term that moves by itself takes its clock as the last argument of `analyticField` and has the implementation advance it in `update` with the real step, the way the curl's does, and never reads the time itself.

#### The streaks

`impls/StreaksInk.ts` with `shaders/streaks.wgsl` and the numbers in `impls/streaks.params.ts`. Thin lines on rays from the middle of the canvas, travelling in, which is the tension drawn: a build lengthens them and multiplies them and the end of the build takes them away. The `riser-streaks` study rests at a count of 0 and an intensity of 0, so it draws nothing until tension lifts it, and then no pass is encoded and nothing is uploaded either.

```
the shared clock: speed x real time, so travel is per second
a streak:   travelled = start + rate x clock        (start and rate: hash of its index)
            whole part = generation                 (ray, length, light, hue: hash of index and generation)
            fractional part = how far along its trip:  0 at the edge, 1 at the eye
```

Nothing is random and nothing is integrated per streak. Placement is a hash of the streak's index and its generation, so the same song draws the same picture, and a streak that reaches the eye is reborn on a new ray at the edge. Everything is placed in pixels and the angle is taken in pixels, so the rays converge on the middle of a wide canvas and a tall one alike. Streaks are born on the canvas edge along their own ray rather than on a circle round it, so on a wide canvas the ones running sideways are not spent off screen. A small eye is left empty and the light fades over the last stretch of a trip, or the light of every ray would pile up at the centre.

The shader draws one instanced quad per streak, six vertices each, so the width is a real number of pixels: `width` is written against a canvas 1080 high and scales with the short side, and `length` is a fraction of it. A line list is one pixel wide on every GPU and would vanish at 4K. The colour is the ribbon's, `ribbonColour` at the key, with `hueSpread` scattering each streak's place in that palette, so the streaks sit with the ribbon rather than beside it. It adds light through `INK_BLEND`, so presence scales it with no shader knowing.

| Knob        | Means                                                      | Range    |
| ----------- | ---------------------------------------------------------- | -------- |
| `count`     | how many are lit; a level, so the last one fades in        | 0 to 96  |
| `length`    | the longest a streak gets, as a fraction of the short side | 0 to 0.6 |
| `speed`     | trips from the edge to the eye per second                  | 0 to 3   |
| `width`     | pixels on a 1080 high canvas                               | 0 to 6   |
| `intensity` | the brightest a streak gets                                | 0 to 1   |
| `hueSpread` | how far the hues scatter round the ribbon's, palette units | 0 to 0.5 |

Each streak's own length and light are between half and all of the knob, and its own rate between 0.6 and 1.4 of the shared clock, so they do not arrive together. Tension climbs the count, length, speed and intensity and thins the width, which is what keeps it sparse: at tension 1 with the onset flux full there are 48 streaks, at most 0.48 of the short side long and 1.5 px wide at 1080 high, which covers at most 3.2% of a square frame and 1.8% of a 16:9 one (`streakCoverage`, and a test holds it under a tenth on every shape). The one fast row is the onset flux on the length, so the streaks flick within a build.

The WebGL2 path skips it: it has one program and only ever drew the fractal, and a cast the director chose without one is stood in for as before.

#### The shards

`impls/ShardsInk.ts` with `shaders/shards.wgsl` and the numbers in `impls/shards.params.ts`. Flat, sharp triangles thrown outward from the middle: the ink for the drop, and held back for it. Nothing is born through a build or a groove, so the pool is empty, and while it is empty nothing is uploaded and no pass is encoded; the CPU scans 192 slots and the GPU does nothing. It is one instanced draw of three vertices a shard, added into the shared target through `INK_BLEND`, so presence scales its light without the shader knowing.

```
impact (the frame the drop lands)   a burst of `burst`, spread over 150 ms, from a ring round the middle
strong sub, bass, lowMid or highMid  three smaller shards, only while `release` is still high,
hit                                  at most `hitRate` hits a second, and never more than two
```

The burst is spread and starts on a ring (0.08 to 0.14 of the frame's height from the middle) for one reason: additive light from a hundred shards born on one pixel on one frame sums to white there, and the picture is a white dot for a frame and not a burst. Spreading the births and starting them off the centre are the two answers, and there is no scaling of the light by how many are alive. Measured on a 160 by 90 grid at 16:9 over the half second after an impact, the worst any frame gets is the biggest burst the knob allows (160) covering 5.6 percent of the frame with at most four shards stacked on a pixel; at rest (48) it is 1.8 percent with two; and at the top of what the study's own mapping reaches, which is a loud, hard, bass-led, busy track (80 shards of 0.06, thrown at 2.0), it is 7.2 percent with four. These are one frame's coverage; the trails then smear it. `shards.params.test.ts` holds bounds on all three, and it draws the same triangle the shader does.

**Time is the only clock.** A shard's place is a closed-form function of its age, `start + reach * (1 - exp(-age / 0.6 s))` along its direction, with its angle turning at `spin` radians a second, and never a step added up a frame at a time. The k-th shard of a burst is born k/N of the way through the spread, and a shard born part-way through a step is that much older at the end of it. So the same song at 60 and 144 steps a second puts every shard in the same place after a second, which the tests check to four decimals, and `burst`, `speed`, `size`, `spin` and `life` are all per second. The pool is a ring: a birth takes the slot of the oldest, so the slot is the birth counter modulo 192, and every choice at birth (direction, distance, speed, spin, size, life, hue) is a hash of the slot and the counter, never `Math.random`. The same song throws the same shards for as long as the ink lives; the director releases an ink six seconds after its study leaves, and one built again starts from counter 0.

**Colour is the ribbon's.** Each shard takes `peakPaletteAt(keyHue + RIBBON_TINT + spread)` from `post/params.ts`, the fluid's palette at the same peak brightness the ribbon uses, with the spread a fifth of a palette either side. That is the same reason as the fluid's emitters: spread over the whole palette the shards would cancel the key. The colour is flat and the same at all three corners, and a shard fades by `1 - (age / life)^2`, so it reads as a solid thing that vanishes and not as a glow.

**Flash safety (WCAG 2.3.1).** One burst is one flash. The extractor rearms `impact` only after the `release` evidence has fallen below 0.096, and a release decays over half a phrase, which is never under 1.5 s. From the 0.28 an impact fires at that is 0.8 s at the quickest, and from a full release 1.6 s, so a song cannot fire more than one every 0.8 s, and a fresh payoff needs a fresh build behind it besides. The pool holds its own floor as well, since a bench button or a host can write `impact` as fast as it likes: two bursts are never less than half a second apart, so never more than two a second, under the three the rule allows. The per-hit births are held by a bucket that holds one hit and refills at `hitRate`, which the pool clamps to 2, so in any second at most three hits throw, whatever the knob says or the mapping does; a hit throws three shards at 0.6 of a burst shard's size, which is about 1 percent of the frame at most, with every knob at the top of its range, well under the large area the rule counts. The tests hammer `impact` on every other step and a bass hit on every step, at 60 and 144 steps a second.

**Cost.** On an NVIDIA Blackwell adapter (Playwright's Chromium, headed, a real WebGPU device) the shards' pass at 2560 by 1440 into an `rgba16float` target cost about 0.01 ms over an empty pass at 48 shards, 0.006 ms at 80 and 0.023 ms at 160 shards of 0.12: the best of five runs of 300 passes in one submission, so an upper bound for one pass's own work and not a whole frame. The demo's `data-frame-ms` read 1.0 ms with and without the ink in a ribbon cast at that size, which is the meter's floor (the renderer clamps a frame to a millisecond) and so says only that nothing came near a budget. The WebGL2 path has no compute and draws the fractal alone; it skips this ink like every other and does not throw.

#### The dust

`impls/DustInk.ts` with `shaders/dust.wgsl` and the numbers in `impls/dust.params.ts`. Slow specks adrift, for the quiet end of a song: intro, rest and outro on a soft, slow track. It has the streaks' shape: one instanced quad a speck, six vertices each, a storage buffer of 160 specks made once and filled on the CPU every frame with finished pixels, added into the shared target through `INK_BLEND` so presence scales the light. A speck is a quad with a smooth falloff in the fragment shader, `(1 - d^2)^2` across its radius, and its size is a real number of pixels against the short side, so it is round on any canvas and survives 4K.

```
two shared clocks, both per second
  travel  = drift x real time              (short sides of the canvas)
  seconds = real time
a speck:  place = head start + own pace x travel along own heading
                  + a slow sway across it, a sine of the same distance     (a gentle curve)
          light = intensity x count level x fade at the wrap x twinkle(seconds, own rate, own phase)
```

Nothing is integrated per speck and nothing is random: every choice is a hash of the speck's index, so the same song draws the same dust, and the same seconds draw the same picture at any frame rate. It does not read the flow. The canvas carries what is drawn on it along the flow and smears it into a trail, so a speck that barely moves is already adrift, which is the reason it is dust and not a second flow. Space wraps, and the fade is what makes that safe: a speck's light is measured from the wrap seam, over 6 percent of the short side, so it is gone before it leaves one edge and comes back after it arrives at the other and nothing pops. The fade belongs to the seam and not to where the speck is drawn, so it holds under the gather.

| Knob        | Means                                                             | Range    |
| ----------- | ----------------------------------------------------------------- | -------- |
| `count`     | how many are lit; a level, so the last one fades in               | 0 to 160 |
| `size`      | the widest a speck is across, soft edge included, px at 1080 high | 0 to 16  |
| `drift`     | short sides of the canvas travelled a second                      | 0 to 0.2 |
| `twinkle`   | how far a speck dims at the bottom of its cycle, 1 to nothing     | 0 to 1   |
| `intensity` | light added on one frame                                          | 0 to 0.6 |
| `hueSpread` | how far the hues scatter round the ribbon's, palette units        | 0 to 0.3 |
| `gather`    | how far every speck is pulled toward the middle, 1 all the way in | 0 to 1   |

Each speck's own size is between half and all of the knob, its pace between half and one and a half of the shared distance, and its twinkle a period of two and a half to ten seconds, so they are never in step. The colour is the ribbon's palette at the key, `ribbonColour`, scattered by `hueSpread` and then taken 45 percent of the way to white, which is what makes it pale.

**Silence is the count's job.** A quiet passage is not silence and is exactly where the dust should show, so the study cannot simply make the dust brighter as the music gets quieter: `energy` inverted on the count is largest at a silent packet. The count is a hump instead. The square root of `energy` lets the dust in with the first sound at all, and a square takes it away as the music fills the frame, so a silent packet resolves to a count of 0 and no pass is encoded, and the peak, about 70 specks, is at an `energy` of 0.45, with 43 at 0.1 and 20 under a full packet. The count carries the gate and not the intensity because it is a level that brings the specks in one at a time, so a sound arriving is a few specks fading up and not the whole field at once; the intensity is an ordinary ceiling that only dims under load. Presence 0 costs nothing as for every ink: the renderer does not build or call it, and one with a count of 0 uploads nothing and encodes no pass.

**Tension gathers it.** `gather` climbs to 0.5 at a full build, which halves every speck's distance from the middle. It stops there on purpose, since at 1 all 160 would sit on one pixel and add up to a white dot, and a test holds the deepest pile-up at a full build to three specks on a pixel. The drop lets them go as tension falls.

**Coverage.** Every speck is a square of its diameter at most, so `dustCoverage` bounds what is lit. At the most the study's own mapping reaches, about 70 specks at a size of 10, that is 0.6 percent of a square frame and 0.34 percent of a 16:9 one. With every knob at the top of its range, 160 specks 16 across, it is 3.5 percent and 2 percent, and `dust.params.test.ts` holds that under a twentieth on seven canvas shapes from a 320 pixel square to 3840 by 1080. It is largest on a square canvas and does not change with a canvas's size at one shape.

**Measured**, on an NVIDIA GeForce RTX 5080 through Chromium's WebGPU in headless Edge. The shader compiles and the console and the device report no errors. In the bench with the dust soloed over a lazy fluid, a synthetic packet at level 0 read a brightest pixel of 2 of 255, which is the grain, so silence draws nothing, and at level 0.3 it read 175 to 199 over several runs with about 0.16 percent of the frame above 8 and 0.015 percent above 64, and the brightest pixel was the same with a flow under it and without one. At level 0.05 it read 179 with 0.09 percent above 8, and at a full level 1 it read 88 with 0.02 percent above 8, so a loud packet thins the dust and does not wash the frame. At tension 0.9 the specks had drawn into the middle of the frame. One pass at 2560 by 1440 into an `rgba16float` target cost about 0.009 ms over an empty pass, the best of five runs of 300 passes in one submission, at the study's peak and at 160 specks of 16 alike, so an upper bound for one pass's own work and not a whole frame. `data-frame-ms` at a 2240 by 1440 canvas read 6.8 ms with the dust and 6.8 without, which is the animation loop's own cap, so it says only that nothing came near a budget. Not checked: a real track, a real flow at a real slow speed for a whole quiet passage, or any other adapter. Those readings were taken at an intensity of 0.25 and a size of 8, which is where the study first rested: at 0.08 the same frame read a brightest pixel of 47. Looked at afterwards as a picture and not as a brightest pixel, as the only ink of a quiet cast over curl drift and through the film look, that left the frame reading as empty, so the study rests at 0.5 and a size of 10, which shows as pale specks with short trails on black; the rows that dim it as the music fills were doubled with it. It is still the number to look at first on a real quiet passage. The WebGL2 path has one program and draws the fractal alone, so it skips this ink like every other and does not throw.

#### The caustics

`impls/CausticsInk.ts` with `shaders/caustics.wgsl` and the numbers in `impls/caustics.params.ts`. Soft moving light like the floor of a pool, for the quiet end of a song on a soft, tonal track: intro, rest and outro. One fullscreen triangle and a 44 float uniform made once, added into the shared target through `INK_BLEND` so presence scales the light. It is the ink most at risk of washing the canvas out, since a caustic is a pattern over the whole frame and the canvas keeps 93 percent of itself a frame. That, and not the look, is what the design is about: only thin lines carry light and everything between them is exactly black.

```text
a surface of four moving sine waves
  where a ray lands   = p + the slope of the surface
  how much that squeezes the plane = the determinant of the map's Jacobian
                        (a closed form: four sines and six products a pixel)
  light piles up where the determinant is 0         the folds of the map, a network of lines

brightness = (1 - (det / BAND)^2), clamped at 0, ^ sharpness, less CUT
             exactly 0 whenever |det| is over BAND, which is most of the frame
```

**Why this method.** The usual cheap caustic iterates a coordinate warp a few times and takes a sharp power of how close neighbouring warped points land. That is the same idea with the determinant left as a number to be measured. Taking the determinant of a real map means the pattern can be checked against the map: `caustics.params.test.ts` differentiates `p + gradient(h)` numerically for the surface the waves describe and holds the closed form to it, and holds its slope to a numerical derivative of the determinant. It costs four sines a pixel, against the dozens of a marched or iterated caustic, and the lines have a structure a warp does not give: cusps where two folds meet, and hairlines where one runs alone. The waves' directions are spread round the circle, their frequencies are not multiples of one another and their rates differ in size and sign, so the network has no grid, does not repeat and churns rather than slides. Their focus, amplitude times wave number squared, is a pure number, so `scale` only stretches the pattern and does not change how many folds there are, which is why the lit share does not depend on it.

**Sparse by construction.** Physically the light goes as one over the determinant, which tails off away from a fold into a haze over the whole frame, and a haze is what the feedback sums into a flat sheet. So the tail is cut: the bump is exactly 0 beyond `BAND`, and `sharpness` raises what is left to a power, thinning the lines. The power leaves each line a faint shoulder, a few percent of the peak and about as much of the frame as the line itself, and the canvas would sum that to fourteen times itself as a halo, so `CUT` is taken off and the rest stretched back. Where the determinant changes fast a fold is thinner than a pixel and would dash and crawl as it moves, so the band is measured against the determinant's own slope and widened to 1.5 pixels there, and the line is dimmed by the same ratio so its light is the same. The pattern is in short sides from the middle, so it is the same shape on a wide canvas and a tall one.

| Knob        | Means                                                                       | Range    |
| ----------- | --------------------------------------------------------------------------- | -------- |
| `intensity` | light added on one frame at the top of a line                               | 0 to 0.6 |
| `scale`     | wavelengths of the coarsest wave across the short side, so cells this big   | 1 to 8   |
| `speed`     | cycles a second of the reference wave; the others turn at their own rates   | 0 to 0.4 |
| `sharpness` | the power the bump is raised to; higher is thinner lines and more black     | 1 to 24  |
| `hueSpread` | how far the hues scatter round the ribbon's across the frame, palette units | 0 to 0.3 |

**Moves per second.** One clock, `phase`, advances by `speed` times the real step, and each wave's offset is worked out from it in doubles and wrapped to a cycle on the CPU, so the shader is handed numbers between 0 and 1 and the sines stay accurate however long the song runs. The same seconds draw the same picture at 30, 60, 144 and 240 frames a second, which the tests check. Nothing is random. The colour is the ribbon's palette at the key, `ribbonColour`, at three places round it (the middle and half the spread either side, already times the intensity), and the shader blends across them along a heading, so the hue shifts across the frame and drifts on a real-time clock of its own: a lap in fifty seconds, and not stopped by a speed of 0.

**Silence is the key's job.** The light is `keyClarity` times its resting intensity, written as the rest value with an `invert` row of the same size on `keyClarity`, so a silent packet resolves to exactly 0 and no pass is encoded, and so does a passage of drums with no key in it, which is right for a tonal study. Energy and hardness dim it (a full packet ends at 0.14 against 0.22 at rest), and on a loud passage with no key those dims meet a gate that is already shut and resolve a little under 0, which the ink holds at 0. Swell has no row on the intensity and lifts the `speed` instead. Presence 0 costs nothing as for every ink: the renderer does not build or call it, and one with no light uploads nothing and encodes no pass.

**Music makes it sparser, not brighter.** `energy` raises the sharpness by 4.5, so a full packet has thinner lines and more black, at a sharpness of 12.5 against 8 at rest. **Tension dims it** through the sharpness too, by 6 at full tension, which thins the lines to a few bright threads. It cannot go through the intensity, because the gate holds that at 0 in silence and a tension row on it would take it below zero on a silent build. `scale` and `hueSpread` sit still on purpose, and the guard in `registry.test.ts` says why: a live scale zooms the whole pattern about the middle, which reads as the camera moving and not as light on water.

**Coverage and the arithmetic.** The canvas keeps `FEEDBACK_KEEP`, 0.93, of itself a frame (Plume's calm trail, which was Drift's, the longest a cast carries), so a still image sums to `1 / (1 - 0.93)`, about 14.3 times what one frame adds. What one frame adds on average is the intensity times the mean of the brightness, so the frame's mean settles at `SETTLE x intensity x mean`. The cast's ceiling bends the light only above half of itself and the lowest ceiling a cast may set is 0.5, so a settled mean under `MEAN_BUDGET`, 0.2, never meets it however long the pattern sits: lines can brighten as they dwell, and the frame cannot fill. `sampleCaustics` measures both on the pattern, over a grid and a spread of times, and `settledMean` does the sum.

| Where                                                      | Intensity | Sharpness | Lit share of the frame | Settled mean |
| ---------------------------------------------------------- | --------- | --------- | ---------------------- | ------------ |
| rest, a clear key                                          | 0.22      | 8         | 8.8 percent            | 0.16         |
| a quiet tonal passage (energy 0.15)                        | 0.17      | 8.7       | 8.5 percent            | 0.12         |
| a full packet                                              | 0.14      | 12.5      | 7.4 percent            | 0.085        |
| a full packet at full tension                              | 0.14      | 18.5      | 6.3 percent            | 0.072        |
| the widest the lines can be, at any scale and canvas shape | 0.22      | 1         | 14.9 to 16.3 percent   | 0.34         |

"Lit" is brighter than 0.05 of the peak. The test holds under a fifth at rest, at a full packet and at the mildest sharpness on every scale and on wide, square, tall and ultrawide canvases; and holds the settled mean under the budget at the worst corner of everything the mapping reaches, which is the resting intensity at the mildest sharpness any packet takes it to. Nothing holds it at the top of the intensity range: a cast that writes 0.6 over these lines is on its own, and the test says so.

**Measured**, on an NVIDIA GeForce RTX 5080 through Chromium's WebGPU in headless Edge. The shader compiles and the console and the device report no errors. Shader against mirror: the ink alone into an `rgba16float` target and read back at 1280 by 720, 1080 by 1920 and 2560 by 1440 with different scales, sharpnesses and clocks, 8.7 million pixels in all, and `causticLine` at the same points differs by at most 0.0009 of the peak, which is half float rounding. #### The halo

`impls/HaloInk.ts` with `shaders/halo.wgsl` and the numbers in `impls/halo.params.ts`. One glow about the middle of the canvas that breathes with the music. It was first written as the ink the director can always fall back on, with the middle of the character space, a reach of 1 and a fit of a half for every moment, and it was in 53 percent of the casts the twenty measured tracks can be given, for the reason the Ribbon was (see "Measured"). It now has a home at the soft, tonal, slower end (the ambient, downtempo, folk and orchestral tracks), a reach of 0.3, a full fit for intro, rest and outro, 0.4 for a groove or a build and 0.15 for a drop, where a glow at the middle is a smaller thing than the hit. It is modest everywhere. It is a companion to other inks and never the whole picture, and it is the one ink that sits where the canvas piles light up. It is one quad sized to the glow, six vertices, and a 12 float uniform made once, added into the shared target through `INK_BLEND` so presence scales the light.

```text
d = distance from the middle in pixels / (radius x short side)      round on any canvas
u = 1 at the peak, 0 at the edge                                    (and at the middle, for a ring)
light = smoothstep(u) ^ exponent                                    exactly 0 at d = 1 and beyond
```

The quad is square in pixels and the light is a function of the distance in pixels, so the glow is round on a wide canvas and a tall one, and `radius` is a fraction of the short side, so it is the same share of the picture on both. A smoothstep has no slope at either end, so the peak is round and the edge arrives without a crease, and it is exactly zero at the radius whatever the other knobs are, which is what lets the quad be no bigger than the glow. `hollow` moves the peak out from the middle to that fraction of the radius, so a kick can open the glow into a ring. The middle is dimmed by `hollow / 0.5` and dark from a hollow of 0.5 up, so a small hollow is a soft disc with a shoulder and not a disc with a pinhole in it, and nothing jumps as it leaves 0. The peak of the profile is 1 wherever it sits.

| ----------- | -------------------------------------------------------------------------------- | ----------- |
| `radius`    | where the glow reaches zero, as a fraction of the short side                     | 0 to 0.7    |
| `hollow`    | where the peak sits, as a fraction of the radius; from 0.5 up the glow is a ring | 0 to 0.9    |
| `softness`  | 1 is broad shoulders and 0 is a tight core; the exponent runs from 1 to 4        | 0 to 1      |
| `intensity` | light added on one frame at the peak                                             | 0 to 0.044  |
| `hue`       | palette units added to the ribbon's colour at the key                            | -0.5 to 0.5 |

**Silence is the radius's job.** `energy` sets the radius through a square root, so the first sound lets a small glow in and a full packet makes it 0.26 of the short side, and a silent packet resolves to a radius of 0 and no pass is encoded. The radius carries the gate and the intensity does not, because a size of 0 draws nothing however much light there is, so tension can lift the light without a silent build lighting anything. A near-silent packet at full tension resolves the radius a little under 0, which the ink holds at 0; `registry.test.ts` names that as the one knob allowed under the floor of its range, and `halo.test.ts` holds that it draws nothing.

**What the music does.** `energy` on the radius, `beatPulse` a little on the intensity (0.004 on a rest of 0.055), `lowEnd` on the hollow (0.5, so a kick opens it to a ring and lets it close), and `hardness` takes 0.4 off the softness so a hard track has a tighter core. Loud, hard and swelling music dims the light, to 0.032 at a full packet, so a bigger glow is a dimmer one and the study never ends a loud passage brighter than rest.

**Tension tightens it to a point.** It takes 0.07 off the radius and 0.15 off the hollow and adds 0.002 to the intensity. A quiet build (an energy of 0.15) goes from a radius of 0.10 to 0.03, still lit, with the hollow at nothing. A full packet at full tension is at 0.034 against a rest of 0.055, so the light a build adds is inside the wash-out guard and needs no entry in `BUILT_LIGHT`.

**The arithmetic.** The halo sits at the middle of a canvas whose flows mostly pull toward that point or push from it, so light accumulates there before it does anywhere else. The canvas keeps 0.93 of itself a frame, so a still image sums to `1 / (1 - 0.93)`, about fourteen times what one frame adds over the floor. The floor is the part that is easy to leave out: a director-built canvas takes 0.018 off every pixel on every frame, which is what keeps a long trail from settling into a haze, so a glow only builds on what it adds above that. The first numbers here left it out. They rested the glow at 0.028 a frame and expected it to settle near 0.4; with the floor under it, it settled near 0.14, and on a real adapter it read as almost nothing at a quiet level and could not be found beside the ribbon. `settledPeak` is `SETTLE x (intensity - CANVAS_FLOOR)`, and a test holds that floor to the canvas it came from. A flow only takes light away from the middle (its velocity is zero there, so what it carries in comes from further out), so that still sum is the most the middle can reach. The feedback pass bends light above half its ceiling, and a director-built canvas holds a ceiling of 1.25 at a full packet, so the knee is at 0.625. The top of the intensity range, `HALO_INTENSITY_MAX`, is the light at which a still image settles exactly there, so nothing a study writes can bend the middle at a full packet.

Not checked: a real track, how it looks over a real flow, its cost as a share of a real frame, or any other adapter. The WebGL2 path has one program and draws the fractal alone, so it skips this ink like every other and does not throw.

#### The rings

`impls/RingsInk.ts` with `shaders/rings.wgsl` and the numbers in `impls/rings.params.ts`. Thin circles born at the middle of the canvas on the predicted beat and spreading outward: the ink for a steady groove and for a build, where a roll of them is the tension drawn. It is one instanced triangle strip a ring, a storage buffer of 24 rings and a 4 float uniform made once, added into the shared target through `INK_BLEND` so presence scales the light.

```text
beatPhase wraps (0.9 -> 0.1)                 a beat, found where the wrap falls inside the step
tempoConfidence under the gate               no ring is born
a ring: radius = 0.04 + travel since birth   travel = speed x real time, in frame heights
        light  = intensity x (1 - progress)^2   progress = the sooner of age / life and the way to the corner
```

**A beat is the phase wrapping, not an onset.** A ring lands where the tracker predicts the beat, so a hat that falls between beats draws nothing and a kick the tracker has not caught draws nothing either. `rate` is rings a beat, snapped to 1, 2 or 4, and a tick is a multiple of 1/n of the phase, counted against the n of the frame it falls in, so a change of rate between two frames cannot birth a burst. A jump backwards, or ahead by more than half a beat, is the tracker moving the phase and not time passing, and births nothing. `tempoConfidence` is gated with a gap between on (0.35) and off (0.25), so a track sitting on the edge does not switch the rings every beat, and the study also sets the light to its rest value times the confidence, so a silent packet resolves to no light and no pass is encoded.

**A small pool, not a closed form of the beat clock.** A ring's radius as a function of the phase alone would be frame-rate proof by construction, but the phase is a prediction and the tracker changes its mind: the period changing would move every ring on screen on the same frame, and a phase cannot become seconds without the tempo. A ring that is born and then simply travels has neither problem. It is frame-rate proof all the same, because nothing is added up per frame in a way that depends on the step: the distance is one shared clock, `speed` (frame heights a second) times the real step, and the birth is placed inside the step by where the wrap falls between the last phase and this one, so a ring born part-way through a step is that much older at its end. The same beat makes the same ring in the same place after a second at 60 and at 144 steps a second, which the tests check to two decimals of a pixel, and through a change of tempo. A ring keeps the life it was born with, so a build shortening the knob does not make the rings on screen vanish. A birth into a full pool takes the oldest, which is the dimmest. Nothing is random: the colour is a function of the birth counter.

The ring is drawn in pixels from the middle, so it is round on a wide canvas and a tall one. `thickness` is written against a canvas 1080 high and scales with the short side, as the ribbon's and the streaks' do, and is the width at half brightness; the light is full inside it, falls by a smoothstep across a soft edge of a pixel (scaled, never under three quarters of one) and is exactly zero past `thickness / 2 + edge`. `speed` is in frame heights, so a tall canvas has more of them to cross. A ring fades as it goes and is gone by the time it leaves: its progress is the sooner of its age over its life and the way it has come over the way to the far corner, so it reaches nothing at the corner and is never cut off at an edge.

| Knob        | Means                                                          | Range       |
| ----------- | -------------------------------------------------------------- | ----------- |
| `rate`      | rings a beat, snapped to 1, 2 or 4                             | 1 to 4      |
| `speed`     | frame heights a second                                         | 0.05 to 0.8 |
| `thickness` | width at half brightness, px on a 1080 high canvas             | 0 to 8      |
| `intensity` | light added on one frame at the ring's brightest               | 0 to 1      |
| `life`      | seconds at most; sooner if the ring reaches the corner first   | 0.3 to 4    |
| `hueSpread` | how far the ring's hue steps about the ribbon's, palette units | 0 to 0.5    |

The colour is the ribbon's palette at the key, `ribbonColour`, and each ring steps a little from the last: a triangle wave over eight rings about the key, so neighbours differ by a quarter of the spread and never by a jump.

**Tension is the roll.** It takes `rate` from 1 to 4, so the spacing halves like a snare roll, and takes 1.5 s off the life, which is what keeps a roll sparse: four a beat at the same life would be a crowd. It leaves the light alone, so a build adds rings and not brightness. Energy thickens a ring by under a pixel and a heavy low end quickens it by a third.

**Coverage.** `ringsCoverage` is an upper bound: rings born every `1 / (n x bpm / 60)` seconds until the pool is full or the first is gone, each at full light, as wide as its light reaches and none overlapping, counting only the part of each circle inside the frame. At the most the study reaches, a roll of four a beat at full tension on a loud, low-heavy passage at 200 beats a minute (the tracker's ceiling), 12 rings are alive at 3.3 px, and they light 3.6 percent of a 16:9 frame, 6.4 percent of a square one and 6.1 percent of a tall one; `rings.test.ts` holds it under a tenth on eight shapes from 640 square to 3840 by 1080, and at rest under a tenth at 60, 128 and 200 beats a minute. It is a bound on the study's own reach and not on the top of every knob: a cast that writes a life of 4 and a rate of 4 over these rings is on its own. On a very small canvas the edge, which never drops under three quarters of a pixel, dominates: 320 by 180 lights up to 8 percent of the same worst case.

**Flash safety (WCAG 2.3.1).** One ring is under 2 percent of a frame, at its thickest and widest on any shape, and a roll is a train of them at the beat's own rate, about 13 a second at the fastest tempo. It is a thin line moving across the picture and never a large-area change of luminance, so it is not a flash by the rule's area test.

**How bright.** The last two inks were first set from a sum on paper and both came out invisible on a real adapter, so this one was set by looking. A director-built canvas keeps 0.93 of itself a frame and takes 0.018 off every pixel, so light that moves does not sum like a still image: a ring sweeps a pixel in a frame or two and the wake is what the floor leaves. `ringPassPeak` simulates it, and a moving ring peaks at exactly what one frame adds (0.8) at any speed the study reaches; at the range's floor of 0.05 it would stand long enough to sum to 2.5, which is why the range stops there. On the adapter in the bench, beside the ribbon at a quiet level, 0.45 was a faint ring that had to be looked for and 1 was bold, so it rests at 0.8: the newest ring reads about as bright as the ribbon and the older ones fade into the black behind them. At a loud level the fluid drags the rings into curls and they stay clear of the ribbon. At full tension and 200 beats a minute the roll fuses into a bright disc round the middle with the rest of the frame black, which is the busiest the study gets.

**Cost.** One instanced strip of 514 vertices a ring, and only the band of it is shaded. At 2560 by 1440 into an `rgba16float` target one pass costs 0.003 ms over an empty pass at rest (5 rings), 0.009 at the study's worst (12) and 0.010 at a full pool of 24 at 8 px, the best of five runs of 300 passes in one submission on an RTX 5080, so an upper bound for the pass's own work and not a whole frame. `data-frame-ms` read 5.6 ms with the rings and 5.6 without, at 2560 by 1440, which is the loop's own cap and says only that nothing came near a budget. With no beat believed, or presence 0, no pass is encoded and nothing is uploaded; the pool still steps every frame so a ring is placed where the beat puts it the moment the light returns, which is a few comparisons.

**Checked** on an NVIDIA Blackwell adapter through Chromium's WebGPU in headless Edge: the shader compiled with no messages and no validation errors (the first cut named a variable `from`, which WGSL reserves, and only the browser said so; a test now keeps names off the spec's reserved list), and the ink alone drawn into an `rgba16float` target at 1280 by 720, 720 by 1280, 1000 by 1000 and 1920 by 1080 (thickness 0.4 to 8, rates 1 to 4, several keys) read back within 0.01 of the TypeScript, 1.6 percent of the peak at worst, with the count of lit pixels within 0.7 percent. Not checked: a real track, a mid-range or integrated GPU, or the picture over a fluid for a whole song. The WebGL2 path has one program and draws the fractal alone, so it skips this ink like every other and does not throw.

#### The spectrum ring

`impls/SpectrumInk.ts` with `shaders/spectrum.wgsl` and the numbers in `impls/spectrum.params.ts`. The bands as bars round a circle: the most literal study in the library, for a groove on any track. It shows the listener the sound itself beside the ribbon, and the trails turn its bars into petals. It has the streaks' shape: one instanced quad a bar, a storage buffer of 96 bars and a 4 float uniform made once, added into the shared target through `INK_BLEND` so presence scales the light.

```text
five bands, sub .. treble     laid along half the circle, mirrored across the axis for the other half
a bar between two bands       a smoothstep of the two nearest: no slope at a band or at a pole
a bar's length                level x (1 + 0.6 x pulse), to a full `length`; a band with no level has no bar
```

**Five numbers made into a ring, without inventing any.** The packet carries five bands and five bars is not a ring, and the ink does not go back to the analyser for more: it reads the levels (rows 0 to 4), the pulses (rows 10 to 14) and the key for the colour, and nothing else. What it decides is only how they are laid out. The bands run along one half of the circle, sub at the bottom of the frame and treble at the top before the ring turns, and the other half is their mirror, so the ring is symmetric and closes without a seam. A bar between two bands takes a smoothstep of the two nearest, which is exactly a band's own value at that band and has no slope there or at either pole, so the mirror is not a crease and neighbouring bars never differ by more than `12 / bars` of the range, the seam and the far pole included. That is the smoothest way of drawing the gap between two measurements and adds none. Each band's pulse kicks the bars that stand for it by the same blend, so a kick lifts the bars at the sub's pole and the ones round it and leaves the treble's alone; it multiplies the level, so a pulse under no level draws nothing. The colour is the same coordinate, the ribbon's palette from one pole to the other on both sides, `hueSpread` wide.

**Nothing is drawn in silence, and it costs nothing.** A bar's length is its band's level, so a silent packet is every bar at nothing and no study knob needs to carry the gate: no pass is encoded and nothing is uploaded, and the same at presence 0, with no light, no count, no length or no width. A bar shorter than a pixel is left out and the rest are packed to the front, so the draw is as long as what is lit.

**Per second, and round.** The ring turns at `spin` turns a second from one shared clock, advanced by the real step and kept under one turn, so a study that moves the spin with the music never makes it jump, and the same seconds turn it the same amount at 30, 60, 144 and 240 steps a second. The bars' lengths take nothing from the frame: they are the extractor's own envelopes as they arrive. Everything is placed in pixels from the middle, so the ring is round on a wide canvas and a tall one, `width` is written against a canvas 1080 high and scales with the short side, and `radius` and `length` are fractions of it.

**Bars cannot overlap.** They stand on a circle, so neighbours are nearest at their feet and only spread further out. `barRadiusPixels` raises the radius to the least that keeps the chord between two feet at a bar's width plus a pixel of edge either side, `pitch / (2 sin(pi / bars))`. The resting 64 bars need 56 px at most and the ring stands at 238 px at 1080 high, so it never bites in the study, and it holds for any cast that raises the count or the width: at 96 bars 8 px wide the radius is lifted to 153 px whatever it is asked for. The canvas carries light from frame to frame and no ink can stop that, but within a frame no pixel is under two bars, which the tests count on a raster.

**The rows.** `energy` on the length (0.05 at rest, 0.18 at full), `beatPulse` on the radius (0.015 of the short side, so the ring breathes on the beat), `pace` on the spin (0.02 turns a second at rest, 0.05 more at full) and `lowEnd` on the width (a kick thickens the bars by a pixel). #### The sparks

`impls/SparksInk.ts` with `shaders/sparks.wgsl` and the numbers in `impls/sparks.params.ts`. Tiny bright points with a short streak along their own velocity, thrown off the treble and upper-mid hits: the groove's constant small gestures, where the shards are the drop's one big one. Every hat and every crack of a snare throws a few, and the canvas's own trail carries them along the flow, so the ink reads no flow. It is one instanced quad a spark, six vertices each, with one 36 byte row of vertex attributes a spark from a buffer of 96 made once, and a 4 float uniform holding the canvas in pixels. It is added into the shared target through `INK_BLEND`, so presence scales the light.

```text
trebleHit or highMidHit        the stronger of the two, from a band that is sounding, once a frame
  where     the hit's centre laid round a circle 0.2 of the short side from the middle
            bottom pole: the low edge of highMid    top pole: the top of treble    two halves mirrored
  how wide  the hit's width fans its sparks across more of the ring
  how many  up to `count`, or whatever the bucket holds; it refills at `rate` sparks a second
a spark    leaves the circle outward inside a cone of 0.4 radians, under a little drag and a little gravity
```

**Where a spark is born, and what was chosen.** The packet says where in the spectrum a band's hit landed (`trebleHitCentre`, `highMidHitCentre`) and how wide it was (`trebleHitWidth`, `highMidHitWidth`), as fractions of the octaves from 20 Hz to 16 kHz. The ink lays the two bands it answers to round a circle, the same way the spectrum ring lays the bands: the low edge of highMid (1 kHz) at the bottom and the top of the treble (16 kHz) at the top, the two halves mirrors of each other, and a coin per spark, a hash, picks the side. A hat, at about 0.9 of the span, lands high on the ring, a snare's crack at 0.7 lower, and a wide hit fans its sparks across more of the ring than a narrow one (`ringPosition`). A ring rather than the ribbon's line because the ribbon can be either a line or a circle at any size and a cast does not hand the sparks the ribbon's knobs; a circle round the middle is the same on either. When both bands fire on one frame the stronger one is the hit, and the treble wins a tie: a hat and a snare together are one struck sound. A band under 0.01 in level throws nothing, which the extractor never asks for and the bench's synthetic packet does, since it writes hits at any level.

**A spark is a function of its age.** Its place is the solution of a point under drag (2 a second) and a little gravity (0.25 short sides a second squared), `start + terminal * age + (speed - terminal) * (1 - e^(-drag * age)) / drag` on each axis, never a step added up frame by frame, so the same spark is in the same place at 60 and at 144 steps a second, which the tests check to two decimals of a pixel. Over its longest life it sinks about 7 percent of the short side. Every choice at birth (which side, how far round, the cone, speed, life, size, colour) is a hash of the slot and a birth counter, never `Math.random`, so the same song throws the same sparks for as long as the ink lives. The pool is a ring and the counter picks the slot, and the most the knobs can keep alive at once, 66, is under its 96, so a live spark is never overwritten. Everything is in short sides of the canvas, so a spark flies the same distance on a wide canvas and a tall one, and its size is pixels on a 1080 high canvas scaled by the short side, with a floor of 2 px: a quad thinner than that can fall between pixel centres on some frames and be hit on others, which reads as flicker.

**The rate is a bucket.** It refills at `rate` sparks a second and holds one hit's worth (`count`). A hit throws as many sparks as it finds in it, up to `count`, so in any span of `T` seconds no more than `count + rate * T` are born whatever the packet does, and a run of sixteenth-note hats at 200 beats a minute cannot throw more than the knob allows. The first cut waited for a whole hit's worth and lost a fifth of the rate: the hits and the refill do not fall on the same frames, so a hat that found three sparks in the bucket and needed five threw nothing. Sixteenths at 174 with a rate of 28 and a count of 5 threw 215 sparks in ten seconds against the 280 the rate allows. `sparks.params.test.ts` hammers a hit on every step at 30, 60, 144 and 240 steps a second and counts any window of a second.

**Colour is the ribbon's,** the palette at the key with `hueSpread` either side. A spark is taken 70 percent of the way to white at birth and cools to the palette over its life, with the white going as the square of what is left, so the head reads as a hot point and the trail it leaves as the key's colour. It fades by `(1 - age / life)^1.5`, so it is bright and then gone and does not read as a glow, and a soft hit throws slightly slower and dimmer sparks than a hard one (0.6 to 1 of the speed and of the light).

| Knob        | Means                                                                    | Range      |
| ----------- | ------------------------------------------------------------------------ | ---------- |
| `rate`      | sparks a second at most; what the bucket refills at                      | 0 to 60    |
| `count`     | sparks one hit throws, a whole number, and the size of the bucket        | 0 to 8     |
| `speed`     | short sides a second at birth, before each spark's own 0.6 to 1.25 of it | 0 to 1.2   |
| `life`      | seconds, before each spark's own 0.6 to 1.2 of it: under a second in all | 0.1 to 0.8 |
| `size`      | the widest across, px on a 1080 high canvas, each spark 0.6 to 1.4 of it | 0 to 6     |
| `intensity` | light added on one frame at a spark's head                               | 0 to 4     |
| `hueSpread` | palette units either side of the ribbon's colour at the key              | 0 to 0.3   |

**The rows.** `pace` on the rate (20 a second at rest, 28 at a pace of 0.4 and 40 at 1), `treble` on the count (3 a hit at rest, up to 6), `hardness` on the speed (0.5 at rest, up to 0.95), `pace` on the life (0.55 s at rest, 0.2 off at full), `weight` on the size (4 px at rest, up to 6 on a bass-led track) and `energy`, `swell` and `hardness` each taking a square off the intensity, 0.5, 0.3 and 0.2. The treble is the tempting row for the light and it would break the wash-out rule, since a bright full packet would draw brighter than rest; on the count it cannot, because the bucket holds the sparks a second and a fatter hit only spends it faster. A full packet draws at an intensity of 1.4 against a rest of 2.4, and never brighter. The spread of the palette is a setting and sits still, with a reason in the registry guard.

**Tension makes the rate climb,** as the catalogue says: it adds 20 a second, so a snare roll that the resting rate would ration is let through, and a full packet at full tension is at the top of the range, 60. It leaves the light and everything else alone. That means it shows on a run of sixteenths and not on a sparse beat: the bench's synthetic pattern throws about 14 sparks a second, under the resting rate, so tension has nothing to let through there and the sparks alive read 6.9 at tension 0 and 7.1 at 1. `studies/sparks.test.ts` throws sixteenths at 174 for ten seconds and holds the count at a tension of 1 to at least one and a half times the count at 0.

**Nothing is drawn in silence, and it costs nothing.** A silent packet has no hit in it, so nothing is born, the pool is empty, no buffer is uploaded and no pass is encoded, and the same at presence 0, with no light or no count. A hit from a band that is not sounding is not a hit. In the bench at level 0 with the synthetic beat playing, the canvas read 0 of 255 everywhere over six frames.

**Coverage.** `sparkCoverage` is an upper bound: every spark as the whole quad it is drawn in, at its widest and with the longest streak its speed allows (the width plus 0.03 s of its own travel), none overlapping another and none clipped by the frame. With the pool full (96) and every knob at the top of its range, which nothing can reach, it is 3.9 percent of a square frame, 2.2 percent of a 16:9 one and 1.1 percent of a 32:9 one; the params test holds it under a twentieth on eight shapes from 320 square to 3840 by 2160, and it is largest on a square canvas. At the most the study's own mapping reaches, a full packet at full tension (60 a second, a life of 0.35, 32 alive), it is 1.1 percent of a square frame and 0.6 of a 16:9 one, and a groove at a pace of 0.4 is 0.13 percent of a 16:9 one. **Flash safety (WCAG 2.3.1):** a spark is a few pixels wide and fades over a fraction of a second, and the whole pool at the very top of every range is under 4 percent of the frame, so nothing here is a large-area change of luminance however fast the hats.

**How bright** was set by looking, on the adapter, beside the ribbon at a quiet level and at a loud one. The sum on paper says a light that stands still settles at fourteen times what a frame adds over the canvas's floor (0.018 a frame off every pixel), and a spark does not stand still: it adds one frame of light where it is and moves on, and the floor eats what is left of the wake. So the intensity is not near 1. At 1 with a 2.5 px spark the sparks were a few faint hairlines you had to look for, the brightest pixel of a frame with one in it reading no more than 163 of 255 and mostly under 100. At 1.6 with 4 px they were still thin. At 2.4 they read at once beside the ribbon at both levels.

| Brightest pixel of a frame with sparks in it, sparks alone | quiet (0.25, 128 BPM) | loud (0.85, 174 BPM) |
| ---------------------------------------------------------- | --------------------- | -------------------- |
| over lazy fluid                                            | mostly 180 to 225     | mostly 190 to 230    |
| over curl drift, the slowest flow                          |                       | mostly 190 to 230    |
| share of the frame over 8 of 255                           | 0.05 to 0.3 percent   | 0.2 to 0.6 percent   |
| share of the frame over 64 of 255                          | at most 0.14 percent  | at most 0.1 percent  |

The dimmer frames, 25 to 165, are sparks near the end of their life. Beside the ribbon in a contact sheet of the bench they read as pale points against a coloured line: brighter than the line at a quiet level and about level with it at a loud one, where the ribbon is at its own brightest. Nothing washes out. The top of the range is 4. It is the number to look at first on a real track.

**The bench.** The synthetic packet writes the treble hit on every off-beat eighth at 0.6 and the snare's highMid hit on two and four at 0.8, each from a band it also gives a level, so the sparks answer it without a change to the bench, and at level 0 it draws nothing. What it cannot show is the ring's placement, which is the same every hit (the hit's centre and width are the band's own middle and full width), and the rate limit, which needs sixteenths. Both are held by tests on packets written for the purpose.

**Cost.** One instanced draw of six vertices a spark. At 2560 by 1440 into an `rgba16float` target one pass with 35 sparks alive, from a hit on every step at the top of every range (60 born a second, each living up to 0.96 s), cost 0.009 ms over an empty pass (0.011 against 0.002), the best of five runs of 300 passes in one submission on an NVIDIA Blackwell adapter, so an upper bound for the pass's own work and not a whole frame. `data-frame-ms` read 5.6 ms with the sparks in a ribbon cast and 5.6 with them at presence 0, at 2240 by 1440, which is the display's refresh and says only that nothing came near a budget.

**Checked** on an NVIDIA Blackwell adapter through Chromium's WebGPU in headless Edge: the shader compiled with no messages, the pipeline and the draw raised no validation error in an error scope around the cost run, and the console held nothing but the browser's own note about `powerPreference`. Not checked: a real track (the bench's synthetic packet only), a readback of the pixels against a CPU model of the fragment shader as the spectrum ring's was, any other adapter, or a whole song at 60 frames a second. The shader and the buffers are checked against each other by the tests: the three instance attributes and their offsets against the struct, the binding, the corners, the head position against `HEAD_AT`, and no name on WGSL's reserved list. With `navigator.gpu` removed in the same browser the bench drew the WebGL2 kaleidoscope, skipped the sparks and logged no error. The WebGL2 path has one program and draws the fractal alone, so it skips this ink like every other and does not throw.

### Post stack

`src/post/PostStack.ts` sits between the inks and the swap chain. An ink never draws on the canvas: it draws into one of two `rgba16float` history textures, and the composite pass is the only thing that writes the canvas.

```
clear ──► inks, in cast order, the ribbon among them
                                     │ add
                                     ▼
          history[current] ──► bright ──► blur x3 ──► composite ──► canvas
                ▲ add                                     ▲
                └── history[other], carried along the live flow, then
                    zoomed, turned, decayed, floored and held under a ceiling
                         ▲
                         └── the blended velocity field, or one zero texel
```

`prepare` writes the uniform, `clear` empties the target, `drawRibbon` is the ribbon ink's pass, and `render` is everything after the inks. They run in that order once a frame, and the split exists because the ribbon draws in ink order and reads the uniform `render` used to write.

Half floats because an ink's brightest cores run well past 1, and in `bgra8unorm` everything above 1 was lost, which is why loud passages used to clip to a flat white blob. They are also filterable, which the warp and the blur both need.

- **Ribbon.** The sound itself drawn as a line, into the shared target in ink order and before the feedback pass, so it is fresh light like the other inks' and the trails carry it into sheets. Off unless a cast holds the `ribbon` ink, and even then it draws nothing until `ribbon.intensity` is above 0. It is one triangle strip with two vertices a point, one either side of the line, so the width is a real number of pixels: a line list is one pixel wide on every GPU and would vanish on a 4K canvas. `ribbon.width` is written for a 1080 pixel canvas and scaled by the canvas's short side, so 4K draws it twice as wide, and the edge fades over a pixel so it is soft without being wider than asked. The blend is additive, and leaves alpha alone.
  - **The points** are 256 floats in a storage buffer that is created once at start-up and never again, and the shader takes the count from the buffer's length. `fillRibbonPoints` in `post/params.ts` fills them from the client's waveform each frame the ribbon runs and uploads them; with the stage off, or at no intensity, or with no audio yet, nothing is drawn and no buffer is written, and the uniform's ribbon block is zeros. The strip has one point more than the buffer holds, which is how the circle closes; the line repeats its last point there and draws a segment of no length.
  - **Shape** is the number `ribbon.shape`: 0 is a horizontal line across the middle, and 1 is a circle about the centre with the waveform as its radius. It rounds up from a half, and there are only the two. A waveform window is not periodic, so the ends of the circle would meet with a step in them; the step is shared out round the ring as a slow tilt under the level, which joins the ends and leaves the shape of the sound alone. `ribbon.height` is how far a full-scale sample moves the line, as a fraction of the canvas: of its height for the line, of its short side for the circle, which rests at 0.28 of that side out. The waveform is drawn as it comes, with no automatic gain, so a quiet track draws a small line and `height` is the knob.
  - **Colour** comes from the fluid's own palette, `paletteAt` in `scenes/fluid.params.ts`, which `paletteLut` is built from, at the song's `keyHue` plus half a palette. The plumes are shades within under half a palette of the key, so the far side of them is a line that reads against the dye and not into it, and it moves with the key like everything else. It is scaled so its brightest channel is 1, because the palette's dimmest stop peaks at 0.34 and its brightest at 0.94, so left as it is the line would be about a third as bright in one key as in another: `ribbon.intensity` is the peak brightness in every key.
  - **The WebGL2 fallback skips it.** It wants the waveform and a strip drawn into the shared target, and that path has neither. A cast that holds it still draws, without the line, and nothing on that path reads its numbers. `data-post` still names the stage, as it names the feedback there whose carry is skipped too.

- **Feedback.** The other history texture, carried back along the live flow, then scaled a little about the middle, turned a fraction of a degree and decayed, added under the new frame. The inks have already drawn into this pass's target, so the pass is additively blended rather than reading its own output. On a still image the gain is `1 / (1 - amount × decay)`, about 1.19 at the defaults; more than that and the field turns into a milky haze. The `amount`, `decay`, `zoom` and `rotate` are written as what one frame does at 60 frames a second, and `feedbackStep` in `post/params.ts` converts them by the real frame step (`(amount × decay) ^ (dt × 60)`, `zoom ^ (dt × 60)`, `rotate × dt × 60`), so a trail lasts and travels the same number of seconds at 60 Hz and 144 Hz and presets look as they always did at 60. The new frame is weighted to match, through the pass's blend constant: it is added once per drawn frame, so without that a faster display piled up more of them and the same still image settled at 1.87 at 144 Hz against 1.19 at 60. A missing step reads as one 60 Hz frame, and the step is held between 1/480 s and 0.1 s. [The canvas plan](docs/canvas-plan.md) replaces this stage.
  - **Carry** is the flow part, and 0 turns it off, which is where the old Plume and Wash rested, each raising it with `energy`. Melt rests at 1, and so does Plume in a calm passage, falling to 0.4 as the track gets loud. At 1 the history under a pixel is read from where the live velocity field says that light was one step ago, so every part of the screen bends its own way rather than the whole picture turning about the middle; that is the one thing MilkDrop has always done and this stack did not. The velocity arrives in the field's own units, grid widths per second, and the pass divides by the same `cover` it multiplied by to find the grid point, so a wide stage and a tall one carry the same distance. The carry reaches the shader as the canvas uv one unit of velocity moves in this frame, worked out on the CPU, so the shader never sees the frame rate here either. A cast with no flow has a single zero texel bound in place of one, so there is one pipeline and no branch.
  - **Floor** is what keeps the blacks black. An ink that adds a constant to every pixel, as the fluid's dye does, has that constant summed by the trail: under a gain `g` it settles at `base / (1 - g)`, which at the 0.94 Plume holds in a calm passage (it was Drift's) is seventeen times the base and reads as an even blue haze over the whole frame. The floor is light taken off the carried history, clamped at zero, so the same constant settles at `(base - floor) / (1 - g)` instead; a floor a little under the base's brightest channel times the gain holds it near black. It comes off the brightest channel and the other two are scaled by the same fraction, for the reason under Ceiling. It is written as what one frame does at 60 frames a second and scaled by the real step, the way the rotation is, so it takes the same light off per second at any rate; the decay compounds rather than scales, so the two only agree exactly as the gain approaches 1, and at 0.94 a 144 Hz display settles a code value or two higher. Being subtractive it takes faint light out sooner than bright light, so a trail lasts roughly its own brightness divided by the floor, in frames, once the decay is near 1. That is the point: MilkDrop's trails read as well as they do because what is left of them sits on black.
  - **Ceiling** is what stops a long trail running away. A gain near 1 sums a still pixel toward `1 / (1 - gain)` and half floats hold 65504, so nothing else would. Below half the ceiling nothing changes; above it the brightest channel bends toward the ceiling and never reaches it, and the other two are scaled by the same fraction, for the reason the Tonemap bullet gives: limiting each channel on its own pulls the three together and bleaches the trail toward white. It applies to the history sample alone, after the decay, so it caps what is carried back rather than what the inks have just drawn. The default is 16, far above anything an ink draws, so a cast that sets no ceiling of its own never meets it. Plume and Melt set one, and pull it in as a passage gets louder and harder so carried light cannot stack into a flat slab of one colour.
- **Bloom.** A bright pass with a soft knee at half resolution, then three levels, each a horizontal blur reading the level above (so it downsamples) and a vertical blur inside its own level. Five taps land between texels, so hardware filtering makes each a nine-tap Gaussian for the price of five.
- **Chromatic aberration.** Red and blue are read either side of green, by an offset growing with the distance from the middle. The split is `amount + beat × beatPulse`, so it opens on every onset and closes again.
- **Grade.** The frame's edges and its colour, in the composite between the bloom and the tonemap, so it costs no pass of its own and the tonemap still bends what the vignette leaves over 1. Three numbers, all neutral at rest, so a look that switches the stage on and says nothing changes nothing.
  - **`grade.vignette`**: 0 is none and 1 is closed down hard to the centre. The clear zone reaches the corner at 0 and the middle at 1, with a soft edge 0.75 wide, so the corners are down to a quarter of their light at a half and the middle of each edge has lost only a fifth: the middle of the range is already plain to see, which a plain power of the distance is not. It follows the shape of the frame, not a circle. `vignetteLight` in `post/params.ts` is the shape, stated so it can be tested.
  - **`grade.saturation`**: 1 leaves the colour alone and 0 is grey. Colour is scaled about the pixel's own luminance and no channel is clamped, for the reason the Tonemap bullet gives: limiting each channel on its own shifts a hue, where scaling all three together only thins it. It stops at 1, because above it the smallest channel of a saturated pixel goes negative and the composite's last `max` would clip it.
  - **`grade.weave`**: gate weave, the whole frame drifting by a pixel or two the way a strip wanders in a projector's gate. It is in pixels at 1080 high, scaled with the canvas's height, and 0 is none and is where every look but `film` rests. It is meant to be felt and not seen: a weave that reads as motion is too much. The path is `gateWeave` in `post/params.ts`, a sum of three sines a side with rates that are no simple ratio of one another (about 0.1 to 0.7 Hz, the fastest a small flutter on the wander), so it never repeats over any span a person will watch and the two axes are not locked into a diagonal or a circle. It is a function of the packet's `time` alone, so it reads the same at any frame rate and the same track weaves the same way twice; there is no `Math.random` and nothing counts frames. The weights sum to exactly 1, so `weave` is the most the frame ever moves, and it moves at most about 2 pixels a second for each pixel of it. The composite samples the picture, the split and the glow at a shifted position; the vignette, the split's centre and the grain stay with the screen, since they are the lens and not the film.
  - **The frame's edge shows no seam.** A frame shifted by a pixel would show one pixel of what lies past its edge, and the sampler's clamp would repeat the last row there, a streak along the border that comes and goes. So the weave crops instead: the frame is read from a span narrowed about the middle by the weave's own reach on each side (`shrink`, under a fifth of a percent of the frame for each pixel of weave), and the offset then moves that span about inside the picture and never off it. `weave.test.ts` reads the two extremes of that span at every moment on four canvas shapes and holds them inside 0 to 1. The crop is fixed by the weave's amount, so a weave that thins as a look leaves thins its crop with it, and there is nothing to snap when the stage switches off. At a weave of 0 both terms are 0 and the read is the frame's own uv exactly, so no cast that does not use it draws a different pixel.
  - **Held to range where it is written.** A row may carry a lane past its end, and `squeeze` does it on purpose: its impact rows undo what tension did, so at a drop with tension already falling the vignette resolves below 0 and the saturation above 1. `writePostUniform` holds both to 0 to 1 and the weave to 0 to `MAX_WEAVE` (4 pixels; a NaN falls to the neutral one), so the shader only ever sees a number it can use, and off writes the neutral numbers rather than branching.
  - **WebGL2 applies the same three numbers.** It is a few lines of the composite there as here, and the vignette's edge width rides in the uniform so the two shaders read one constant. The offset and the crop are worked out on the CPU in canvas uv, so the two paths read the same floats.
- **Tonemap.** A shoulder rather than a curve over the whole range: below it nothing changes, above it a value bends toward 1 and never reaches it. Rolling the brightest channel and letting the other two follow keeps a pixel's colour; rolling each on its own bleaches it toward white. An extended Reinhard over the whole range was tried first and made every track flat and muddy.
- **Grain.** A hash of the pixel and a clock, added at the end.

Each stage has an `enabled` flag and the stack has its own; a stage runs only when both are on, and what is on is decided by what is live: the canvas switches the feedback on, a ribbon ink switches the ribbon on, and the looks switch on the stages they name. `post/params.ts` holds the defaults and `writePostUniform`, which resolves every toggle on the CPU and writes the 208-byte uniform each pass reads, thirteen vec4s, so the shaders have no branches. The last ninety-six of those bytes are the flow block, the floor, the ribbon's two vec4s, the grade and the gate weave, in that order, so every float before them is where it always was; the flow's `cover` reaches the first of them through `writePostUniform`'s one optional argument. A ribbon that is off, or has no light or no width, writes all eight of its floats as zero, and its pass is not run at all. With every stage off the composite is a straight copy.

`postSummary` names the stages that are running in pass order, `ribbon` first when a cast holds that ink, and that line is what the canvas's `data-post` prints. Only Melt holds it (Drift did until it was folded into Plume), so Plume and Prism print exactly what they did before the stage existed. `grade` sits between `chroma` and `tonemap` and is off unless a look names it: none of the three shipped casts' looks does, so all three print what they always did, and only `squeeze` and `film` print it.

It also holds `POST_LANES`, one read and one write per number a study may name, so a mapping onto `bloom.intensity` writes that one lane each frame rather than rebuilding the object. `bloom.weights` is deliberately not a lane: it is three numbers and nothing wants a feature riding on it.

At 3840 by 2160 the stack holds about 176 MB: two full-resolution history textures and six smaller ones.

### Presets, which are now pinned casts

A preset is one JSON file under `src/studies/casts/`, and it is the whole of what the stage draws with. It names studies rather than a scene, because the picture is several small pieces at once:

```json
{
  "id": "plume",
  "name": "Plume",
  "flow": "lazy-fluid",
  "inks": ["dye-plumes"],
  "look": "warm-soft",
  "canvas": {
    "knobs": { "feedback.amount": 1, "feedback.decay": 0.9 },
    "mapping": [{ "from": "energy", "to": "feedback.decay", "gain": -0.23 }]
  },
  "overrides": {
    "dye-plumes": {
      "knobs": { "dye": 0.8, "colourShift": 0.5 },
      "mapping": [{ "from": "harmonicChange", "to": "dye", "gain": 2 }]
    }
  }
}
```

One flow, one to three inks, one look, and the canvas. `flow` may be left out, which is a picture nothing carries and is what Prism is. `canvas` is the feedback: it is the picture itself rather than a look, so swapping a look does not throw away what the canvas holds, and `"enabled": false` leaves the picture with no history at all. Its knobs are a patch over the stack's own feedback defaults.

`overrides` is what the cast changes about a study it holds, and only for studies it holds. Its `knobs` patch that study's resting values and its `mapping` rows are added after the study's own, so a cast can only push a study further in the direction it already goes; a knob or a row aimed at something the study's implementation does not have is an error naming the file and the path. That is why the studies carry the smallest gain of the five presets they were first written from and each cast adds the rest.

A mapping row reads exactly as a preset's did:

```
value = knobs[to] + Σ gain × curve(field[from])
```

`from` is one of thirty packet fields, plus `lowEnd` for the louder of sub and bass, plus `presence`, which is not in the packet: it is the director's fade. `tension` is packet row 47 and is among the thirty, but the resolver still takes its value as an argument, so the study bench can wind it by hand and the director can pass on the one it chose by. Five of the packet fields are the song-scale ones above, which move over tens of seconds rather than per frame, three are the harmony, two the structure, two the beat as a clock and four the moment. Five are the per-band pulses, `subPulse` through `treblePulse`. The raw per-band hits are not among them, for the reason `onset` is not: they are events rather than levels, and an implementation reads an event straight from the packet. `impact` is an event and is among them anyway, because it is published as a pulse rather than as a flag: it is 1 on the frame the drop lands and falls away in a fifth of a second, so a row on it reads like a row on `beatPulse` and fires once a drop rather than once a beat. `to` is a knob of that study's own implementation and nothing else, so two studies in one cast cannot fight over the same number by accident. `curve` is `linear`, `square`, `sqrt` or `invert`, all of which keep 0 at 0 and 1 at 1 except the last. `gain` may be negative, which is how a feature thins a number rather than raising it: `treble → viscosity` at −0.18 is the fluid keeping its detail when the music is busy. Several rows may name the same knob and they add.

All of it is resolved on the CPU, once a frame, in `studies/resolve.ts`, and nowhere else. That is why a cast can send treble to a knob that used to take bass without a line of WGSL changing. `resolveLive` writes into an object the renderer owns and keeps, since this runs every animation frame.

Nothing on screen is static, in every cast and every study added later. `src/studies/castMapping.test.ts` walks `PRESETS` and fails, naming the cast and the stage, when a stage is on and no lane of it lands anywhere else at some packet than at silence, and fails again when a flow or an ink it holds does not move at all. `src/studies/registry.test.ts` sweeps every study and every cast at both ends of tension, keeps every knob inside a safe range, holds the feedback gain under 1, and asserts that a full packet leaves `intensity`, `saturation` and `tonemap.exposure` at or below rest: a loud, hard passage puts its force into motion and structure, and pulls the light back rather than adding more. A new cast is covered without touching either.

Prism and Melt resolve to the numbers their 0.1 presets did, and Plume to its own (below), which `src/studies/cast.test.ts` and `src/gpu/Renderer.test.ts` both check against `casts/preset-frames.json`, a capture of the preset path's own output taken before it was deleted, except for Plume's five frames, which were written from the folded cast once and are its record from then on. ### Plume

Plume, Wash and Drift were three pinned casts of the same three studies (a fluid, `dye-plumes` and `warm-soft`) at different numbers. On 2026-09-20 they were folded into one cast at the owner's request, and `wash.json` and `drift.json` are gone. What it took from each:

- **From Plume**, the dye reactivity: `harmonicChange` on `dye`, `lowEnd` and `novelty` on `hitDye`, and `energy` on `dye`.
- **From Wash**, the colour, exactly: `colourShift` rests at 0.5 on top of the study's `keyHue` row, so the palette sits half a turn from the key, and `lowEnd` shoves it by 0.25 squared.
- **From Drift**, the calm trails: amount 1, decay 0.94 at rest, carry 1, and the floor and ceiling rows as they were. There is no ribbon.
- **From Wash again**, the short trails when loud: the canvas amount falls to 0.3, the decay to 0.68 and the carry to 0.4.

**Which route the two fluids took.** A cast has one `flow` and no way to give a member a presence, and `blendKnobs` only cross-fades two studies while the director is changing between them, so a pinned cast cannot hold both fluids and fade them by the music. Plume holds `lazy-fluid` alone and moves that fluid's own knobs from `energy` toward the turbulent tuning: the vorticity rises from Drift's 18 to Turbulent fluid's 26, the orbit slows from 0.19 toward its 0.1, the velocity decay and force rise with the level through the study's own rows, and the viscosity thins a little. The viscosity cannot go further, because the treble already takes 0.18 of it and a cast that took more would put a full packet below zero, which is no solve at all. The emitter count and the voice stay the lazy fluid's, since a count that followed the level would jump the layout each time it rounded to another whole number.

**Why the trail moves two knobs.** The canvas keeps `amount x decay` of itself a frame. Moving the decay alone to 0.68 with the amount at Drift's 1 would leave a loud trail more than three times Wash's, 0.68 a frame against 0.2, so `energy` takes the amount to 0.3 as well. `rest` adds up to 0.03 to the decay, so a breakdown at a middling level still reads as calm to the trail. Everything is per second: the canvas knobs are what one frame does at 60 frames a second and `feedbackStep` converts them, with the weight of the fresh frame converted alongside, which `cast.test.ts` holds at 60 and at 144 frames a second at both ends of the cast.

**Left out on purpose.** Wash's treble row on `hitDye`. At a full packet the hit dye is 2.55 (a rest of 0.55 and one each from the low end and novelty) and the row would make it 3.75, past the 3.1 the old Plume reached and near double Wash's 2.1, so it pushes the frame past what either cast drew. A gain of about 0.5 would stay inside the old Plume's, and it is one row to add. The saturation stays Plume's and Drift's, a rest of 0.65 plus `keyClarity`, so a loud song is not oversaturated where Wash rested at 1.

The old ids still work. `findCast('wash')`, `findCast('drift')` and `castOrDefault` on either return Plume, through a small map in `studies/casts/index.ts`, so a host that pins by id at a tagged release does not break. `CASTS` lists three, so a picker built from it shows three. **`data-preset` prints `plume` for either**, since it prints the id of the cast that is drawing.

Where the numbers are. Calm is `energy` 0, `rest` 1 and `swell` 0.5, and loud is `energy` 1, `rest` 0 and `swell` 0.5, with every other feature at 0 so the reactive rows add nothing to either. The zoom includes the beat term at a phase of 0.

### What means what

Cast files are compiled in rather than fetched, so `studies/cast.ts` throws at load rather than falling back. ```

```
casts/broken.json: overrides.dye-plumes.knobs.vorticity is not a knob of dye; it has dyeDecay, intensity, …
casts/broken.json: dye-plumes needs the fluid implementation live in the same cast
```

### Studies

A preset in 0.1 named one scene and owned the whole picture. A study is smaller: one piece doing one job on the one shared canvas, so several of them run at once and the song can swap them as it goes. `src/studies/` holds the contract, and nothing there touches the GPU; what draws each one is under Implementations above.

```
FLOW            INK                 LOOK
how the         what is drawn       how it is
picture moves   into it this frame  shown
```

A study is data, not code, because two things read it: the renderer that draws it and the director that picks it.

```ts
type Study = {
  id
  name
  kind: 'flow' | 'ink' | 'look'
  impl: ImplId // what draws it; two studies may share one
  home: Character
  reach: number // where in the song's character it belongs
  moments: Moments // intro, groove, build, drop, rest, outro
  knobs: Record<string, number> // resting values, its implementation's knobs
  mapping: StudyMapping[] // what makes it move, tension included
  cost: 'cheap' | 'medium' | 'heavy'
  excludes?: string[] // studies it may not share a cast with
  requires?: ImplId[] // implementations it needs beside it
}
```

A mapping row reads what a preset's does, plus one field that is not in the packet. `tension` is the song winding up and is packet row 47, but the resolver still takes it as an argument, so the study bench can wind it by hand and the director can pass on the value it chose by. `presence` is what the director fades a study by, 0 to 1; a flow or an ink is handed it and decides for itself what fading in means. Two things are faded by the resolver instead. The ribbon is drawn by the post stack, which knows nothing of presence, so its intensity is scaled here. And looks are blended by presence, normalised, so one look alone is wholly itself and two at a half each land halfway. A stage only one of them has (grain, the split, the grade) fades by its strength knobs, `LOOK_STRENGTH_KNOBS`, so it thins to nothing before it switches off, while its other knobs are averaged only among the looks that have the stage. Each strength knob has a neutral value, `LOOK_NEUTRAL`, which the looks without the stage count as: 0 for all of them but `grade.saturation`, which rests at 1, so a look leaving with its colour drained heads back to untouched and never below what it had, where a fade to 0 would drain it toward grey on the way out and snap it back when the stage switched off.

**Film** is the look for the quiet end of a song, the one place the other looks have nothing to say: heavy grain, a resting vignette and a slight gate weave, for the intro, the rest and the outro of a soft, slow track. It enables bloom, tonemap, grain and grade, and costs what a look costs, which is nothing beyond the composite: no new pass, no new texture, and the weave is a shifted read of the picture the composite already samples.

- **More film in the quiet.** Grain (`grain.amount`, 0.026 at rest, twice Warm and soft's) and weave (`grade.weave`, 0.6 px at rest) both take `energy` inverted, so they are most there when the music is barely there: 0.04 of grain and 1.2 px of weave in silence, the resting figures when it is loud.
- **The vignette breathes with `swell`.** It rests at 0.32 and a passage lifting opens it while one falling away draws it in, so a steady one sits at about 0.22, the corners down by a fifth.
- **Tension tightens even this.** It closes the vignette by 0.15, drains the colour by 0.1, thins the bloom and stills the weave (gain -1, so a loud build has none left). A build settles the frame before it winds it up.
- **It does not wash out.** Exposure rests at 0.96 and the colour at 0.92, a stock held back, and both only fall as the music gets loud; `registry.test.ts` holds a full packet at or under rest, and `film.test.ts` states it again. The bloom is softer than Warm and soft's: a wider knee, less of it.
- **It fades cleanly.** `grade.weave` is a strength knob (`LOOK_STRENGTH_KNOBS`) with a neutral of 0, so against a look that has no grade the weave thins to nothing as film leaves, and the crop that comes with it, and the stage switching off is not seen.

**Squeeze and impact flash** are the two looks that tell the build-to-drop story, and both are a post stage's numbers and no pass of their own, so each costs what a look costs, which is nothing beyond the composite.

- `squeeze` rests as a plain clean look. Tension closes `grade.vignette` (0.6 at a full build), drains `grade.saturation` (to 0.45, well down and not grey) and tightens the bloom, raising its threshold and thinning its glow. Every one of those rows has an `impact` row the other way and the same size, so at tension 1 the drop undoes the build exactly, and at less it overshoots: the drop is when tension is already falling, and the frame of the drop has to be wide open then and not at what is left of the build. The grade stage is what holds the overshoot to none and untouched.
- `impact-flash` is one row: `impact` lifts `tonemap.exposure` by 0.2, so the frame of the drop is at 1.2 and it is within a percent of rest in about half a second. It is built to the flash rule and not tuned to it. The rate is the extractor's: `impact` fires on the `release` evidence crossing up through 0.28 and rearms only once it has fallen under 0.096, and `release` falls with a time constant of half a phrase, at shortest 0.75 s, so two can be no closer than 0.8 s, which is at most two flashes in any second (WCAG 2.3.1 allows three) and in a real track is a section. The size is the gain, since `impact` never exceeds 1, so the lift is capped at 0.2; a cast that puts rows of its own on the exposure is adding to that cap and should say so. `looks.test.ts` feeds it impacts at that quickest rate at 30, 60 and 144 frames a second and counts the exposure crossing its threshold. It is the one study allowed to end a full packet brighter than rest, because a full packet has `impact` in it: `registry.test.ts` takes `impact` out and holds the rest to rest, then holds the lift to its cap.

`fractal-glints` is the one that had to earn its name. It draws the raymarched fractal, and until it had a threshold it drew every pixel of it, which on a canvas that carries fills the frame to the ceiling inside a second. It now rests at a `glint` of 0.3 and rises with the two things that fill the frame, `energy` and `release`, reaching 0.85 at a full packet, where it lights under a quarter of the worst frame there is. Its resting `intensity` is 0.5 rather than the 1 it was ported with, because 1 was tuned for Prism, which has no feedback, and everything the director builds carries; Prism's cast puts it back. Tension sweeps its zoom in, which is the catalogue's own entry for it.

**Curl drift** is the flow for the quiet moments, on the analytic flow's `curl` term. It rests at 0.02 field widths a second at the fastest point, about 50 pixels a second across a 2560 wide canvas, which is a drift you see over half a minute and not a motion you see over a second. It is not still at a silent packet: a flow draws nothing, so what it does there is carry what is left of the picture at that resting speed, and an outro fading to black keeps turning as it goes. Loudness (0.05) and a lifting passage (0.02) speed it; `pace` makes the cells finer and `weight` larger, and `pace` also hurries the pattern's own evolution. Tension speeds the drift (0.06) and the evolution (0.05), so a riser in an intro reads as the picture beginning to churn, and at tension 1 with a full packet the speed is 0.15, about 385 pixels a second at the fastest point. Its home is the middle of the space with a reach of 1, because the catalogue gives it no character. **The dye cannot sit under it**: `dye-plumes` requires the fluid, and a cast has one flow, so a cast on curl drift takes its ink from the ones that draw without a fluid (the ribbon, the streaks, the shards, the fractal) and is never a dye cast. That will change with the quiet inks the catalogue lists (dust, caustics, chord petals), which draw into any field.

**Beat pump** is the flow for the groove and the drop of a steady, hard track: a zoom that kicks outward on the beat and settles back before the next, on the analytic flow's `radial` term with `falloff` 0, so it is a plain zoom about the middle. It reads `beatPhase` (see "The beat as a clock"), which is 0 on the beat and rises to 1, and the whole of it is two rows: `beatPhase` at -0.24, which is the highest point on the beat and falls in a straight line to the next, and `tempoConfidence` through a square root at +0.12, which is the offset that makes the mean over a beat zero. At a confidence of 1 the radial speed is +0.12 field widths a second on the beat, 0 half a beat later and -0.12 just before the next, and the picture is pushed out exactly as far as it is pulled back, so it breathes about where it was and does not walk off the edge. The feedback pass moves the history with the velocity, so positive is outward. `beatPhase` with an `invert` curve peaks on the beat too and would draw the same line; the offset is not a resting value because a resting value would leave a stuck phase pushing.
Rows add and do not multiply, so nothing here can scale the pulse by how sure the beat is, and it does not fade. The tracker keeps the phase running through a bar of doubt, so at a confidence of 0 with a phase still running the pulse is as deep as ever. What the confidence row takes out is the constant: the phase is stuck at 0, the top of the sawtooth, from the start of a track until a tempo has been found, and with any resting offset the picture would be pushed outward for as long as that lasts. At a silent packet, and at any packet before a beat has been found, the study resolves to 0 and the flow encodes no pass. In a doubted bar with the phase running there is a slow inward drift, -0.12 at the very worst, which the canvas's own outward zoom largely cancels. The gate that does fade it is the director: the home is 0.9 on `steadiness`, the reach 0.5, so a track without a steady beat is never handed it, and one that loses its beat has it faded out over a glide. Tension cannot make the swing bigger for the same reason, so it widens it: `falloff` rises to 1.5, which takes the mean speed over a 16:9 frame up by two thirds and the rim down by a tenth, and the mean over a beat is still zero at every falloff. `beatPulse` is left out on purpose, because a decaying pulse with a positive mean is a net outward push at any gain.
The swing is about 2.5 percent of the scale at the rim at 128 BPM, 36 px at 2560 wide, and it is a velocity, so it scales with the length of a beat: 1.8 percent at 175 BPM and 3.5 at 90. That is more than twice what the canvas's own beat zoom swings, and that row is one-sided (`carriedCanvas` zooms out at 9 percent a second and faster on the beat, and never in), which makes it a surge and not a pump. The 0.24 is the number to look at first on a real track: too deep judders the whole picture and too shallow is invisible. Like curl drift it cannot have the dye under it, so a beat pump cast draws the ribbon, the glints and the halo. `beatPump.test.ts` holds the sign, the net over a beat at three frame rates, the silent packet and the director's pick.

**Tunnel** is the flow for the groove and the build of a steady track: `radial` at a small constant with `falloff` 0, so the speed is proportional to the radius and the picture streams out of the middle and off the edge. It rests at 0.04 field widths a second at the rim, 100 pixels a second at 2560 wide, loudness adds 0.04, and tension is the study: it adds 0.15, so at the top of a build the rim moves at 0.23, which is under half of implode's pull at the same point. It is not still at a silent packet, for curl drift's reason. A little swirl keeps it from being a dead straight zoom: 0.002 turns a second at rest, about 10 degrees at the rim, a chord change turns it further through `harmonicChange` (0.012), and tension winds it a little (0.008).
**It goes outward, and the catalogue says inward.** The canvas keeps its history, so the light is drawn where the inks are, near the middle, and the history is what moves. Outward is light leaving where it was drawn and rushing past, which is what flying forward looks like; inward is light shrinking away from where it was drawn. Every cast the director builds already zooms outward at about 9 percent a second, so an inward tunnel would first cancel that and sit still at a radial of about -0.05 before it moved the picture the other way, where an outward one adds to it. Outward flow leaves through the rim and inward flow piles the history up in the middle, where the halo already piles light. And a build that speeds up outward runs straight into the radial burst, where implode is already the inward build. The direction is one sign on the radial rows if it looks wrong on the adapter.
It takes the early part of a build on a steady track, because a build still carries a groove weight while tension climbs and the tunnel suits both: on the scripted song it is the flow of the build for the house and hardstyle characters, and the lo-fi one has it for a second before implode takes over. Implode keeps the build once it weighs about three quarters or more of the moment on a lo-fi track, and a house track, which is steady and sits at the middle of everything else, never has it (nor did the hardstyle one on the scripted song). Its home is steady and nothing else, and its reach is 0.5. It cannot have the dye under it either. `tunnel.test.ts` holds the direction, the plain zoom, the silent packet, the tension row and the director's pick.

**On the scripted song** (`director/song.fixture.ts`, the flow each part spends most of its time on; a cast lands a few seconds after its part begins, since the extractor confirms a section late, so the first seconds of a part still hold the last one's flow):

| Part         | Lo-fi      | House      | Hardstyle  |
| ------------ | ---------- | ---------- | ---------- |
| intro        | lazy fluid | lazy fluid | lazy fluid |
| groove       | lazy fluid | beat pump  | beat pump  |
| build        | implode    | tunnel     | tunnel     |
| drop         | turbulent  | beat pump  | beat pump  |
| breakdown    | lazy fluid | lazy fluid | curl drift |
| groove again | lazy fluid | beat pump  | beat pump  |
| outro        | lazy fluid | lazy fluid | beat pump  |

Before the two, house had lazy fluid for both grooves and hardstyle turbulent fluid; every build was implode and every drop turbulent. A hardstyle groove is the pump's and a lo-fi one never is: `beatPump.test.ts` plays the song at three characters and counts the frames.

A cast is what is live at once: one flow, one to three inks, one look, a patch over each of them, and the canvas they draw on. The feedback lives on the cast rather than in a look, because it is the picture itself: swapping a look must not throw away what the canvas holds. A pinned cast is a cast with an id and a name, for a host that wants a fixed look, and the three files in `src/studies/casts/` are Plume, Prism and Melt written that way. Prism and Melt resolve to the same numbers their presets did, which `cast.test.ts` proves at five packets; Plume is the old Plume, Wash and Drift folded into one; the deliberate differences are in that folder's header.

A cast can only say one flow and one look, and the middle of a change has two of each. So the entry point for anything that fades is `resolveLive`, which takes a plain list of `{ id, presence, override }` and the canvas; `resolveCast` is that over a cast's own studies. A study at presence 0 is not resolved and is not in the output.

`registry.test.ts` walks every study: a knob with no row driving it has to be on an allow list with a reason, every flow and ink has to say what tension does to it, no knob may leave its implementation's safe range at silence or at a full packet, and a full packet may not leave the light or the colour above rest (`intensity`, `saturation`, `grade.saturation` and `tonemap.exposure`), with one argued exception, the flash above, which is a lift by `impact` alone and capped. That last rule is held at tension 0 for every study. At full tension it is held too, except for a light a study says a build may bring in: `BUILT_LIGHT` in that file gives a ceiling and a reason, and the only entry is the riser streaks' intensity, which rests at 0 so that nothing draws without a build.

`data-scene` is derived from the cast's inks, in `sceneOf`: it is the first of them whose implementation used to be a scene, so the dye reads `fluid` and the fractal reads `kaleidoscope` and the three pinned casts print what their presets did. A cast whose inks were never scenes, a ribbon on its own, prints that ink's implementation instead, so the line still says what is drawing.

The director chooses the cast and fades studies in and out as the song goes; a pinned cast is one of these with every presence at 1. `tension` is packet row 47 either way.

### The director

The thing that chooses which studies are on screen. `src/director/`, four files of pure domain logic: no GPU, no DOM, and nothing that reads the clock. It is handed the packet and the real `dt` once a frame and hands back a `LiveCast`: whatever is live, each with a presence, the canvas they draw on, and the tension. That is the same shape a pinned cast is turned into, so the renderer draws either without knowing which it has.

```text
every frame:   character (slow)  ─┐
               moment (medium)   ─┼─►  score = closeness to home × moment fit
               section, recall   ─┘

at a section boundary, or on impact:
   pick a cast  =  1 flow  +  1 to 3 inks  +  1 look
                   inside the cost budget, honouring excludes and requires
   a section that comes back gets the cast it had

between boundaries:
   presences glide (seconds), nothing pops
   a challenger needs a clear margin to unseat a member
   tension is passed on for every live study to read
```

Three pieces feed it. `character.ts` is where the song sits in the five axes, smoothed over tens of seconds from `pace` and `tempo`, `weight`, `keyClarity`, `tempoConfidence`, `hardness` and `grit`, and it says how settled that reading is. It is also where each row is stretched onto the range an axis is meant to use, and where the hardness axis is built out of two rows; see "The axes are stretched, the rows are not" below. `moment.ts` is where in the song we are, as six weights that always sum to 1: build from `tension`, drop from `release`, rest from `rest`, groove from what is left, and intro and outro taken out of groove and rest by position, never out of build or drop. `score.ts` is the one line above, and both halves have to be positive for a study to be cast.

The rules, each with a test in `director.test.ts` (the two about intro and outro have theirs in `moment.test.ts`):

- **Changes land on the music.** A cast is picked on a change of `section` or on `impact`, never on a timer. The extractor confirms a section about six seconds late, so a `novelty` spike starts a fade toward a challenger and the confirmed section settles it. One more thing asks, once: the frame the character is first known (about half a minute in, or never when the host handed one in). The opening cast is picked in the first fraction of a second, while the character is a guess and the best pick is the neutral one, and a track that then gives no signal is left on it. A real metal track read one section, no impact and no novelty spike in two minutes and played all of it on lazy fluid and warm soft. It is asked the way a novelty spike is, so a cast that already suits the track keeps its seat, and unlike the other fast signals the answer is remembered for the section, since what the section was handed before was a guess.
- **The drop is a cut.** On `impact` the new cast is whole inside a tenth of a second. Everything else glides over seconds. The trigger sits at a half and not near the top: `impact` is 1 for a single frame, and one packet read late at 30 frames a second already sees 0.83, so a trigger at 0.9 lost the drop to one janky frame.
- **A drop keeps its cast for its section.** `release` lasts a phrase by design and a drop section lasts many, so once a drop has cut to a cast, novelty spikes choose nothing until a section that began after the drop is confirmed. Measured on a real track before this rule: the drop cut at 1:46, something new entered eight seconds in, novelty spiked with `release` already at 0.06, the pick read plain groove and glided back, and a thirty second drop got eight seconds of its cast. A section confirmed within about seven seconds of an impact began before the drop or at it (the extractor confirms about six seconds late), so it neither re-picks nor recalls; and only the one confirmed near that six seconds, which is the section the drop itself opened, is remembered by the drop's cast. One confirmed sooner is the build, and remembered that way the next build would open on the drop's picture.
- **A flow that leaves no ink is passed over.** The flow is chosen before the inks, and an ink can need what only some flows bring: `dye-plumes` needs a fluid under it. A better-scoring flow of another implementation (curl drift, in an intro or a rest, for most characters) would leave every ink the moment likes with nothing to sit on, and a pick with no ink is no pick at all: the director keeps what is on screen, which at the start of a track is nothing. So the next flow in rank order is tried until one leaves an ink. `pickCast` has the tests, and `studies/curlDrift.test.ts` holds every character at intro and rest to a cast with an ink.
- **No flicker.** A challenger has to clear the margin over a sitting member to unseat it. Close scores change nothing.
- **A section that comes back gets the cast it had**, keyed on the section id in the packet. A cast picked before the character is half settled is not remembered, because it is the neutral opening guess, and a track that opens straight into its main groove would be handed that guess every time the groove returned.
- **Determinism.** Same packets in, same casts out. Any tie-break is seeded from the section id and the settled character, never `Math.random` and never the clock. The character is read for the seed once, when it has settled, and rounded to quarters. Hashed afresh at every boundary to sixteenths, it undid the determinism it was there for: real packets differ a little between two plays of a track, and some axis was within that little of a rounding edge at most boundaries.
- **Variety without randomness.** Where several studies score within the margin of one another, a section rotates among the top few by its rank, so the second verse gets a cousin of the first rather than a copy. A returning section still recalls its own.
- **A build beginning is a signal.** A build has no boundary of its own until it is six seconds old, and a riser creeps in with no novelty spike; on the first real track the build's own section was confirmed after the drop it led to. So `tension` rising through 0.6 re-casts the way a novelty spike does, once per build, and is heard even while a drop's cast is held, since a build starting is the drop's section over. It sits at 0.6 because that is where the build already outweighs the groove; tried at 0.4 it fired while the sitting cast still won, and was spent.
- **A drop that fired is a whole drop.** The packet's `tension` and `release` read 1 when a build or a drop is wholly there, which is the estimator's doing; see "What is published" under the moment rows. It matters here because read as raw evidence a real drop was four tenths drop and six tenths groove, so a study written for drops alone scored 0.4 against about 1 for one that suits groove and drop both, and was never cast, on a real track or on the scripted song. A drop that has fired also ends the build: tension is slow to let go and is still high on the frame of the impact, so the build's weight is cut by the drop's.
- **The chosen cast's canvas carries.** A pinned cast brings its own canvas. A cast the director builds has no file to read one from, and used to get the post stack's defaults, where `feedback.carry` is 0: no flow moved the picture at all, the fluid showed only through its dye, and a flow that draws nothing, as implode and radial burst do, did nothing. It now draws on `carriedCanvas()`, the numbers of the Drift cast that is now Plume's calm passage, which were tuned by eye for a dye ink and the ribbon, plus one row that shortens the trails as tension rises. The study bench draws on the same one.
- **The first thirty seconds.** Until the character has settled, every study is placed the same (`UNHEARD_PLACE`, 1, the best a closeness can be), so the moment fit and the tie-break decide the opening cast and the track drifts into its own family as the reading settles. Half settled is half of each. The score used to read a study's `reach` here, which handed the opening of every track to whichever study had the widest welcome, and a sitting member then kept the seat on its margin: the Ribbon, and the halo and the spectrum ring beside it, opened nearly every track. A wide reach says a study can sit anywhere, not that it is wanted there. On a silent or neutral start the moment reads half intro and half groove, and the opening cast is lazy fluid, dye plumes, halo, beat rings and warm soft, where it was lazy fluid, dye plumes, halo, the spectrum ring and warm soft. The beat rings draw nothing until a beat is believed, so what shows is the dye and the halo; it is there because it ties the caustics and the dust on the moment and sorts first. On the scripted song the first twenty seconds are lazy fluid, dye plumes, halo, caustics and warm soft for all three characters, where they were curl drift, halo, caustics, dust and warm soft: the flow has a groove half to play with as well as an intro, and curl drift has none.
- **A study at presence 0 is not in the output at all**, so the renderer never touches one that is off.
- **A pinned cast turns the director off.** Given one it returns that cast at presence 1 and nothing else, and still passes tension through. It still reads the character and the moment, since a host saves the character for the next play of the track and the overlay shows both. The stage pins at its own level rather than through this option, because a host builds a fresh cast object for every knob it changes and rebuilding the director around each of those would restart the reading every time a slider moved.
- **An intro is where the track is, not how quiet it is.** It used to be a quiet passage early on, so a track that opens at full energy, which is most heavy music, had no intro and its opening read as groove. Now it is read off how much has been heard and how many sections have been confirmed, and it is taken out of groove as well as rest: all of the quiet and half of the room groove would have had (`INTRO_LOUD_SHARE`), held for the first 8 seconds and gone by 30, since intros run from about 8 seconds to about 30 and the clock has to end one that never confirms a change. The sections end it sooner: the first confirmed change is the sign the track has started, and a passage that comes back is a certain one and cuts it off outright. Both are eased and not stepped, so nothing jumps as a boundary is confirmed. Only half of a loud opening, because every study made for an intro was made for a quiet one and dims as the music gets loud: read as all intro, a riff at full energy was cast as curl drift and dust for its first half minute, an empty picture under the loudest part of the track. At a half, a quiet opening is still curl drift and a loud one gets a full picture until its first section brings the track's own cast. Build and drop are never cut by it, so a track that opens on a build or fires an impact in its first seconds still reads one. It counts sound only, so silence before the first note is not intro time used up. With a playhead and a duration, the spans scale by the track's length against a typical three minutes, down to a quarter, so a one minute track has a count-in and not thirty seconds of intro; and the clock is then the later of the seconds heard and the position, so a seek into the middle of a track is not read as its opening.
- **An outro is where the track ends, when it can be told.** With a playhead and a duration, the last tenth of the track (between 4 and 30 seconds) is an outro, leaning in over its first half. It is taken out of groove as well as rest, so a track that ends loud has one, and it is cut by tension, so a track that ends on a build does not have one while it is still winding up. Without them the outro is read as it always was, off the shape of an ending; see the end of this section.
- **Frame rate independence.** Ninety seconds of packets at 60 and at 144 frames a second produce the same cast changes at the same times, within one frame.

**The axes are stretched, the rows are not.** A packet row is built to say one thing truly, and none of them was ever asked to use the whole of 0 to 1. `pace` is a count of hits against four a second, `weight` is a centroid between two groups no mix reaches, `tempoConfidence` is a correlation. Read straight into the character, twenty real tracks landed in one small corner of the space: hardness ran from 0.11 to 0.43 and weight from 0.64 to 1.00, so every study sat about the same distance from every track and the character decided almost nothing. Seventeen of the twenty got the same cast. The owner heard that as "my heavy metal songs look like everything else", and he was right twice over, because the order was wrong where it mattered most: metal read the softest of the twenty.

So `character.ts` maps each row onto the range it really uses, with the ends measured rather than guessed, and `rowsForAxis` is the inverse of that for anything that has to write a row and have it read back as an axis (the study bench, and the fixtures in the tests). The rows themselves are untouched: they are public API, Musimo pins a tag, and a preset's mapping reads them raw.

| Axis         | Reads                       | Stretched from | Ends measured at                                         |
| ------------ | --------------------------- | -------------- | -------------------------------------------------------- |
| `drive`      | `pace` and `tempo`          | 0.22 to 0.78   | Wilco 0.28, Kate McGill's strummed guitar 0.72           |
| `weight`     | `weight`                    | 0.6 to 1       | Subtronics 0.65, Christian Loffler 1.00                  |
| `tonality`   | `keyClarity`                | not stretched  | Skepta 0.00, John Summit 0.83; it already uses its range |
| `steadiness` | `tempoConfidence`           | 0.05 to 0.8    | Adagio for TRON 0.02, FISHER 0.78                        |
| `hardness`   | `grit`, moved by `hardness` | not stretched  | Christian Loffler 0.00, the demo's dance track 0.79      |

`hardness` is the axis that was measuring the wrong thing rather than measuring it too narrowly, and it has its own row now. `grit` carries it and row 46 moves it a third of a step either way, so a four to the floor kick and a dry snare still count for something and a track whose hits are mush is still softer than one whose hits crack. What a listener calls hard is distortion and noise, a mix with nowhere left to go, and energy held in the upper mids, and that is what `grit` measures; see the row under "The song rather than the frame".

**Measuring it again.** `scripts/character-table.mjs` plays a list of local files through the real extractor and prints the mean and the spread of every row the character reads, of the five axes, and of the cast each track is given in a settled groove. It is not a browser: the extractor's whole input is an analyser frame and a `dt`, so `scripts/analyser.mjs` works out what an `AnalyserNode` would have handed it (a Blackman window over the newest 4096 samples, an FFT, each magnitude over the FFT size in dB, which is the spec's own arithmetic, and `AudioGraph` sets the analyser's smoothing to 0, so there is no state to carry). ffmpeg decodes the file to mono at 48 kHz. Twenty tracks of 150 seconds take 25 seconds, which is about 120 times real time, and that is what makes calibrating an axis a loop rather than an afternoon.

```
npm i --no-save playwright-core                  # only for the browser one
node scripts/character-table.mjs --from 60 --to 150
node scripts/character-table.mjs --list my.txt "M:/a.flac"
node scripts/character-table-browser.mjs         # the same table off a real AnalyserNode
```

The list is an argument or `scripts/tracks.local.txt`, which is git-ignored, so nobody's library ends up in the repository. `character-table-browser.mjs` is the slow path that keeps the fast one honest: it drives the demo in headless Edge and reads `window.visimo.features()` while the track plays. Over four tracks the two agree on `pace`, `weight` and `hardness` to within 0.03 on three of them, and disagree by 0.2 on `weight` for one, which is the one reading to take from the browser and not from Node.

The twenty characters that came out of it are in `src/director/tracks.fixture.ts`, and `director.test.ts` holds the library to them: every study has to win a seat for at least one of the twenty at one of the six moments, and a groove has to cast at least eight of the twenty differently. Before this, a groove cast three of them differently and metal, folk and ambient all got the same picture. `fairness.test.ts` holds how often each study is cast over the same twenty, at every moment and both stages of the reading: the Ribbon at most 35 percent, no ink over 45, every ink cast at least once for a known track. The share table is under "Measured".

The options, all of them on the constructor:

| Option         | Default       | What it is                                              |
| -------------- | ------------- | ------------------------------------------------------- |
| `budget`       | 8             | what a cast may spend: cheap 1, medium 2, heavy 4       |
| `margin`       | 0.06          | how far ahead a challenger has to be to unseat a member |
| `glideSeconds` | 3             | how long an ordinary change takes                       |
| `cutSeconds`   | 0.08          | how long a change on `impact` takes                     |
| `variety`      | 3             | how many of the top scorers a section may rotate among  |
| `start`        | neutral (0.5) | a starting character, for a host that knows the track   |
| `studies`      | the registry  | anything that is a `Study`                              |
| `pinned`       | none          | a fixed cast, which turns the choosing off              |

Two things it cannot do. **Outro, for a host that gives no playhead and duration.** The director is never told how long the track is, so it reads an outro off the shape an ending has rather than off the position: a long fall in loudness with no tension under it, in a track that has already run a minute and a half. That catches a fade-out and a track that thins out over its last chorus, and it cannot tell either from a long quiet passage two thirds of the way through a long mix. It never sees one in a track that ends at full energy on the last beat, which is most of dance music, or in a track under a minute and a half. A host that gives the playhead (the `playhead` prop, under [Use](#use)) has the last two solved, and the first stays, since the shape is still read beside the position and is not gated by it. And **the first thirty seconds** are a guess: the character needs 10 to 30 seconds of sound before it means anything, so the opening cast is a quiet one picked by the moment alone rather than the track's own. A host that knows the track can hand in `start` and skip the drift, though the reading still counts as unsettled until the music has been heard.

**Turning it on.** The stage's `preset` prop says what is on screen, and `"auto"` is the director:

```tsx
<Stage hud={hud} preset="auto" fluidSize={512} onUnsupported={...} />
```

It is the same prop as a pinned cast, and not a second one beside it, because the two are one question: only one thing can be on screen, and a `director` flag next to a `preset` would let a host ask for both at once and leave the package to decide which wins. Pass a `PinnedCast` and the song chooses nothing; pass `"auto"` and it chooses everything.

**A starting character.** The reading is a guess for the first ten to thirty seconds of a track, so a host that knows what is playing can hand in where it opens:

```tsx
const [saved, setSaved] = useState<Partial<Character> | undefined>(() => load(track))

<Stage
  preset="auto"
  track={track}
  startCharacter={saved}
  onCharacter={(character) => save(track, character)}
  ...
/>
```

`startCharacter` is a partial of the five axes, so a host that knows one thing about a track says only that; anything it leaves out opens neutral. It moves where the drift starts and not how long it takes, since a reading is still unsettled until the music has been heard, and it is taken until the first frame is drawn and ignored after that, which is what lets a host pass a fresh object on every render.

`track` is what makes it work for a second song. Everything the director holds is about one track: how settled its character is, which cast each section had, and the seed its rotation counts from. Left running into the next song, the opening thirty seconds are never a guess again, a section is handed the cast another track's section of the same number had, and the new track's `startCharacter` is never read. So when `track` changes the director starts again, from `startCharacter` as it stands at that moment. The canvas is not emptied: one track into the next is a change of cast like any other. A host that passes no `track` gets a session read as one long song. The extractor starts again with it, for the same reason: its sections, its tempo and the scales it measures a boundary against are all about the track it has been hearing.

`onCharacter` is the other end of it: the character once the reading has settled, and once every thirty seconds after that, which is the slowest of the reader's own smoothers and so the soonest a number is worth writing down. It hands over a copy, since the reader writes one object in place every frame. It fires under a pinned cast as much as under the director, because the song is read either way: pin Plume for a whole track and the next play can still open where that track actually sits.

**A playhead.** `step(features, dt, playhead?)` takes the position and the length as an optional third argument, anything with `currentTime` and `duration` in seconds. The renderer passes the stage's `playhead` ref on every frame, so it is read fresh and follows a seek; it is the host's and not the song's, so `track` changing does not clear it.

The renderer steps the director on every frame whatever is drawing, and what it chose is drawn only when nothing is pinned. That is also why turning Auto on mid-track lands on a cast already chosen for the song rather than on an opening guess.

### The study bench

The bench is for judging one study, or a small cast, without hunting for the right eight bars of the right song. It lives in the demo and nowhere in the package's exports. Run `npm run dev` and press **Bench** at the top of the right-hand panel, beside **Presets**. A bench setup is kept in the URL hash, so copying the address (or the panel's **copy link**) shares it, and opening one lands straight in the bench.

```text
solo a study ─► [flow] [ink ink ink] [look] ─► the renderer draws these, not the preset
                    │
   live audio  or  synthetic packet
                    │
   sliders write only the rows they own ─► packet ─► every study, and the director
```

What each control does:

| Control                            | What it does                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| solo                               | Puts one study alone. Its own slot takes it, and the other kinds take the plainest studies the cast parser accepts beside it: cheapest first, then the widest `reach`. Soloing the dye ink gets a fluid flow, since it draws nothing without one.                                                                                                                                                                                                                                                                                                                                                                    |
| flow, ink, look                    | The slots, one flow (or none), one to three inks and one look. Any of them can be changed after a solo. A cast the parser would refuse (two inks that exclude each other, a dye with no fluid) is drawn as far as it can be and the parser's own message is shown.                                                                                                                                                                                                                                                                                                                                                   |
| presence                           | 0 to 1 per live study, written into the cast in place. At 0 the study is not resolved, built or drawn, as under the director.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| synthetic packet                   | Off, the real packet is used, so a track has to be playing. On, nothing is heard: the bench writes every row itself.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| bpm, level                         | Synthetic only. A four to the floor beat at that tempo (kick on every beat, snare on two and four, hat between), with the band hits, pulses, `onset`, `beatPulse`, `tempoBpm` and `beatPhase` a real one would write. `level` is the loudness, written into `energy` and the band levels, since a silent packet draws nothing. The ribbon reads a matching synthetic waveform.                                                                                                                                                                                                                                       |
| character                          | The five axes. Each writes the packet rows the director reads it from, through `rowsForAxis` in `character.ts`, which is the inverse of the reading: `weight`, `keyClarity` for tonality, `tempoConfidence` for steadiness, drive to both `pace` and `tempo`, which is what the reader averages, and hardness to `grit`, leaving `hardness` at the reading that neither lifts nor lowers. The numbers in the rows are therefore not the number on the slider, because the reader stretches a row onto its axis; what comes back out is. Studies read those rows, so a study sees the same numbers the director does. |
| moment                             | `tension`, `release` and `rest`, packet rows 47 to 49. The resolver reads tension from row 47, so the slider is the only tension there is.                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| impact                             | Fires row 50 once: 1 on the next frame, then the extractor's own fall (1/e in 0.18 s, `IMPACT_DECAY_SECONDS`). It raises the row and never lowers it, so a real impact under it is still a 1. It does not move `release`; set that yourself to see a drop.                                                                                                                                                                                                                                                                                                                                                           |
| hold (the tick beside each slider) | Over a live packet a slider takes over its row only once it is ticked, and dragging it ticks it. Everything unticked is the music's. Over a synthetic packet everything is in force and the ticks are locked.                                                                                                                                                                                                                                                                                                                                                                                                        |
| packet                             | The five rows a build and a drop move, as the packet actually is after the overrides.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| director would cast                | What `pickCast` puts on screen for the character and moment as the packet stands, with the smoothing taken off: the character is read straight from the rows and the moment as mid-track, so a high `rest` is a rest and not an intro. The bench draws its own slots, so this is a comparison and not a command.                                                                                                                                                                                                                                                                                                     |
| knobs, rest to now                 | Every knob of every live study: its resting value and what the mapping resolves it to this frame, read only. A knob that has moved is blue, so tension is seen winding them.                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| frame time                         | See below.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |

**Reading the frame time.** It is the gap between drawn frames as the renderer measured it, averaged and the worst, over the last two seconds of drawing. It is not GPU time. A cast that costs less than a frame reads the display's refresh (16.7 ms at 60 Hz, 8.3 at 120), and the number only rises above that when the cast costs more than a refresh, so a study cannot be shown cheaper than the display allows. A capped ink such as the fractal draws at its cap and reads that (near 14 ms at 72 frames a second). The renderer clamps one frame to 100 ms, so a hitch longer than that reads 100. To state what a study costs, read the cast with the study at presence 1 and again at presence 0 with everything else left alone, at the canvas size the claim is for, and compare the averages; the worst is what a viewer sees as a stutter. Both readings sit on the refresh until the cast is expensive enough to miss it.

The hash keys are `bench=1`, `flow` (a study id or `none`), `inks` (comma separated), `look`, `p.<id>` for a presence not at 1, `syn=1`, `bpm`, `level`, and one key per held slider (`drive`, `weight`, `tonality`, `steadiness`, `hardness`, `tension`, `release`, `rest`). It is read as untrusted: an unknown study, a study of the wrong kind or a number that is not one falls back to the default for that part and never throws. It is written a quarter of a second after the last change with `replaceState`, so the back button leaves the page and does not walk through every slider position.

The renderer's side of it is one method, `renderer.setBench(bench | null)`, separate from `setPreset`. A `Bench` is `{ live, frame?, waveform? }`: a `LiveCast` to draw in place of the pinned cast or the director's, a function called once per drawn frame with the packet and the real `dt` after the packet is written and before anything reads it, and samples for the ribbon. While one is set it stands over both, the director is still stepped on the packet it left behind, and clearing it hands the picture back to whatever was there and starts the director again, as a new track does: what it read in the bench was the sliders and a synthetic beat, and left standing it would choose for that character under Auto until the half minute smoothers drifted back. A new cast empties the canvas, so a study is judged on its own trails; the same cast handed again does not. It is a development hook and a host has no use for it. `window.visimo` in the dev build is unchanged, since the demo imports the renderer directly.

## Upgrading from 0.1

0.2 removes the per-scene preset union. The stage now draws a cast: one flow, one to three inks, one look and the canvas they share. Musimo pins a tag, so 0.1 keeps working; this is what to change when it moves.

**The prop.** `VisualizerStage` no longer takes `scene`. Delete it. `preset` stays, and what it takes is a `PinnedCast`.

```diff
-<Stage hud={hud} preset={presetOrDefault(chosen)} scene={scene} fluidSize={512} ... />
+<Stage hud={hud} preset={presetOrDefault(chosen)} fluidSize={512} ... />
```

**Drop any character you saved.** The character axes are read from the packet differently now: each row is stretched onto the range it really uses, and `hardness` is mostly the new `grit` row rather than row 46 (see "The axes are stretched, the rows are not"). A number saved by `onCharacter` before this change means something else on this side of it, so a host that keeps them should throw them away once rather than hand them back to `startCharacter`, where they would aim the opening cast at the wrong corner for the first half minute of every track. Nothing else moves: the prop, the callback and the shape of a `Character` are all as they were, and a host that saves nothing has nothing to do.

**The packet is 52 floats, not 51.** `grit` is row 51. Rows are only ever added at the end, so every index a host already reads is where it was, and anything that sizes a buffer from `PACKET_LENGTH` gets the new length for free.

**Prism and Melt look as they did; Wash and Drift became Plume.** Prism and Melt resolve to the numbers their presets did at every packet, which `casts/preset-frames.json` and the two test files that read it hold them to, apart from Melt's flow, which now answers the music (see the end of the Presets section). A host test that pins `wash` or `drift` and asserts `data-preset` on either name has to assert `plume`.

## Adding a study

1. Its own file, `src/studies/defs/<id>.ts`, exporting the study by name (`FRACTAL_GLINTS` in `fractal-glints.ts`): an id, a kind, the implementation that draws it, where it sits in the character space, how it suits each moment, its resting knobs, its mapping and its cost. Then one import and one row in `STUDIES` (`src/studies/registry.ts`). Anything several studies use goes in `src/studies/defs/shared.ts`. `registry.test.ts` then holds it to the bar in `docs/studies-handoff.md` without anyone adding a line.
2. If it needs an implementation that does not exist: an id in `IMPL_IDS` and its knob list in `IMPL_KNOBS` (`src/studies/impls.ts`), a `FlowImpl` or `InkImpl` under `src/impls/` or `src/scenes/`, shaders under `src/shaders/`, and a branch in the renderer's `buildFlow` or `buildInk`. A flow that is a velocity you can write down needs none of that: it is a term on the analytic flow, which is a coefficient and a few lines, under The analytic flow above.
3. A `*.params.ts` holding the pure numbers, with a `*.params.test.ts` beside it. Keep the GPU objects out of it, the way `fluid.params.ts` and `post/params.ts` do; that file is where the implementation's decisions are testable.
4. A row in the study table above.
5. To ship it as a preset, a cast JSON under `src/studies/casts/` and a line in `src/studies/casts/index.ts`.

The demo picks up the study and its knobs on its own. Three things to know before you start:

**An ink adds light; it does not own the frame.** The renderer clears the shared target once and every ink draws over what is there, at its presence, through `INK_BLEND`. An ink that fills the frame every frame washes the canvas out, which is what Melt's first cut did, so state its worst-case coverage and keep it sparse.

**Presence 0 must cost nothing.** No passes encoded, no buffers uploaded. The renderer will not call an implementation at 0 and will not build one, but an implementation that keeps a timer running or uploads on `update` regardless will still cost.

**Name a bind group layout rather than deriving one wherever two pipelines share a bind group.** `layout: 'auto'` derives a layout holding only the bindings a shader happens to read. In the particle scene that was here before, taking the feature packet out of the render shader dropped binding 0 from that layout and every bind group built for both halves became invalid: it drew nothing and the console filled with validation errors. Anything with a compute half and a render half has the same trap waiting.

`src/gpu/math.ts` is a camera basis that nothing calls, left from an earlier raymarched scene. The fractal builds its ray in the shader and does not use it. It is kept and still tested, for the next implementation that wants a camera.

### Measured

| ------------------- | --------------------- | --------------------- |
| 320 by 320, ratio 1 | 8.3, 8.2, 8.3, 8.4 ms | 8.4, 8.3, 8.3, 8.3 ms |

No cell left the cap on any track, at either grid, with either cast, and the whole post stack cost nothing measurable against a straight copy: both sat at 8.2 to 8.4 ms. The white-out the stack was built for is gone. Without it, one of the drum and bass tracks drove a third of the frame to a flat white mass with no structure in it; with it the same moment is a warm core fading into the colour of the scene.

Tempo was the weak part. Replaying those recordings through the extractor as it then ran, Donkey Rhubarb read 140 for 59% of readings, Above & Beyond 129 for 62%, and both drum and bass tracks read 111 to 115, two thirds of the truth, because the dotted-quarter pattern of their drums correlated more than the beat. A 3:2 rule that fixed one broke the other and was not kept. The tracker has since been rewritten (the `tempo` bullet above says how) and the real-track figures have not been re-measured; what has been measured is synthetic drums, rendered to samples and read back through a stand-in for the analyser (`src/audio/synthetic.ts`), which is what the numbers below are.

The two-step is the hard case because nothing in it plays on every beat: the kicks are a dotted quarter apart and the snares a half bar, and every band on its own is periodic at the half-bar or the bar. It reads 174 because the summed envelope has an event on every beat, kick or snare or hat, and reads 87 when it does not; the half-bar is a level of the metre and reading it is a choice of octave, where the 116 the old tracker read on real tracks was no level at all and gave a phase that drifted against the music. On a 30 Hz frame the 30 ms flux lag is a single frame and the choice is marginal: without the octave hysteresis it flipped between the two every few seconds, and with it the half-bar, which the first full window chose, is held. The hysteresis only counts once the window has filled, because the first readings come from a window too short to reach the bar and lean to the half-bar at every frame rate; locked in from there, the two-step read 87 at 60 and 120 frames a second as well. Nothing drives off the tempo in the shipped studies yet; the phase and the confidence are there for the study that will.

The analytic flow was measured separately, on Windows in headless Edge against a real NVIDIA Blackwell WebGPU adapter (RTX 5080), at 2560 by 1440, playing the demo's own track under Auto for three minutes: 720 half-second samples of `data-frame-ms`. The 239 samples on which the cast held Implode read 6.670 ms on average and the 481 without it read 6.673, both sitting at the animation loop's own cap of about 6.67 ms, so nothing left the cap and the flow cost nothing measurable. `data-detail` read `512 fluid + 128 analytic` through the change, which is the mismatched-size blend running, and the console carried no WGSL or validation message on any frame. What that run also says is that the moment rows are still calibrated for synthetic structure: over the whole three minutes `tension` never passed 0.49 and `release` never passed 0.41, so Implode reaches about half the pull its numbers describe and Radial burst is never cast at all, since a flow whose only moment is the drop cannot outscore one that also suits the groove while `drop` and `groove` are complements. Neither is a property of the studies; both are the estimator's, and the handoff says those rows have not been tried on real tracks.
